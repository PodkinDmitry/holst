## 2. Воспроизводимый дефект

В CHAT 09 `onSaveView()` использует атомарный CAS и увеличивает локальную `baseline` только после положительного ответа. Если хранилище **действительно записало** вид, но ответ потерялся, `baseline` остаётся старой. Следующее сохранение того же экземпляра отвергается как `XOD_VIEW_CONFLICT` — **ложный конфликт с собственной записью**. При неизвестном результате нельзя и автоматически повторять операцию: она может всё ещё выполняться на сервере.

Отрицательный контроль: базовый координатор CHAT 09 на новом наборе — **2/12 PASS, 10/12 FAIL** (не поддерживает `session.reconcile()`). Воспроизведено на имитации CAS.

### Новый API (совместимый с CHAT 09)

После `const session = await coordinator.openView(scope)` доступен `session.reconcile()`, который **только читает** хранилище, не повторяя CAS.

| status | Что установлено | Поведение |
|---|---|---|
| `clear` | Нет неопределённой записи | Обычное сохранение доступно |
| `observed` | Более новая ревизия содержит **точно запрошенный JSON-вид** | Обновить локальную baseline; дальнейшие сохранения разрешены |
| `conflict` | Более новая ревизия содержит **другой** вид | Не менять удалённое состояние; показать `remoteView` и `pendingView`, запросить явное решение |
| `unconfirmed` | Ревизия ещё не изменилась | **Не считать запись отменённой:** удалённый CAS может завершиться позже. Повтор опасен; оставить запрос неразрешённым |

- Исключение/некорректный ответ **из самого `compareAndSwap`** отмечается как неизвестный исход. Ошибка `read()` или определённый `{ok:false}` без коммита не блокирует продолжение.
- Пока существует неизвестная запись, новый `session.onSaveView` отклоняется с `XOD_RECONCILIATION_REQUIRED`. Очередные задания не отправляют второй CAS в обход проверки.
- `session.reload()` **по явному пользовательскому решению** загружает серверный вид, обновляет baseline и отбрасывает неподтверждённое локальное намерение. Хост обязан сохранить/показать пользователю несохранённую конфигурацию перед таким действием.
- Для сопоставления видов используется структурное сравнение JSON: порядок полей объекта может измениться при сериализации; порядок элементов массива значим. Входы не мутируются.
- Существующие `transaction(mutator)`, `onSaveView(view)`, `openView(scope)`, `dispose()` и формат хранения остаются совместимыми. CHAT 10 idempotent preset adapter продолжает работать.

### Пример безопасного хостового подключения

```js
const session = await cas.openView('youtube-main');
async function onSaveView(view) {
  try {
    return await session.onSaveView(view);
  } catch (originalError) {
    let status;
    try { status = await session.reconcile(); }
    catch (_) { throw originalError; } // ошибка чтения не означает неудачный CAS
    if (status.status === 'observed') return; // серверное состояние уже соответствует запросу
    if (status.status === 'unconfirmed' || status.status === 'conflict') {
      // SOL: отдельно показать пользователю проблему и явные пути разрешения.
      // Не делать автоматический onSaveView(view) или reload()!
    }
    throw originalError;
  }
}
```

**Не использовать проверку строки `ACK_` из браузерного стенда в реальном XOD** — это имя искусственной тестовой ошибки, не промышленный API. В реальном хосте нужно анализировать `status` и структурированные ошибки.

## 5. Критичные границы

1. **Тестовое CAS-хранилище** линейризуемо внутри Python/Node; реальную атомарность XOD, IndexedDB/серверное хранилище, восстановление после перезапуска и реальные Chrome/Edge на ПК пользователя не проверяли. Без настоящего CAS CHAT 11 не защищает данные.
2. `unconfirmed` при неизменённой ревизии — **не доказательство неуспешной записи**. Нельзя создавать автоматический Retry, пока потенциально выполняющийся коммит не завершён или не отклонён авторитетным источником. Для безопасного удаления/ручного повторения после разрыва связи хосту может потребоваться request-id/серверный receipt.
3. `observed` означает лишь, что **текущее содержимое** удалённого вида совпадает с намерением. Это не криптографическое доказательство того, какой именно клиент совершил запись; для сохранения нужного итогового состояния этого достаточно.
4. У UI CHAT 10 пока нет собственной панели разрешения `XOD_RECONCILIATION_REQUIRED`. **Хост SOL должен добавить UX для `conflict/unconfirmed`** (проверить состояние, загрузить удалённую версию, явно переприменить локальную версию) и не позволять кнопке Retry создавать новую запись без проверки.
5. Патч не отменяет уже начатый CAS; не изменяет публичный интерфейс таблицы и предыдущее исправление SOL уникальности сортировок/глубины фильтров.
