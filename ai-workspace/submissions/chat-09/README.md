# XOD · CHAT 09 — атомарные ревизии вида для нескольких вкладок

**Дата:** 21.11.2026. **Исполнитель:** 🟦 CHAT. **Статус:** референсный CAS-координатор + тесты готовы; **не встроен** в локальную сборку SOL. Ветка `ai-workspace`; `main` не менялась.

## 1. Текущий шаг

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.6. Текущий шаг · 🟦 CHAT — защита от межвкладочных конфликтов.`

## 2. Почему CHAT 08 недостаточен

CHAT 08 создаёт одну очередь read→modify→write **в рамках одного экземпляра координатора**. Две разные вкладки имеют отдельные JS-окружения и очереди: без атомарного сравнения ревизии в хранилище они всё ещё могут перетирать данные друг друга. Также разные редакторы *одного scope* должны обнаруживать устаревшие версии, а не молча сохранять поверх чужих изменений.

## 3. Контракт, который SOL может подключить

`xod-cas-view-coordinator.js` (UMD/Node, без DOM и внешних зависимостей) предоставляет `createXodCasViewCoordinator({read,compareAndSwap,maxAttempts?})`.

**Атомарная обязанность хранилища:**
- `read()` возвращает `{revision, data}`, где `revision` — уникальный для каждой коммитнутой версии документа токен (строка или safe integer), `data` — полный JSON-объект.
- `compareAndSwap(expectedRevision, nextData)` **атомарно** записывает новый снимок *только если* текущая ревизия документа равна `expectedRevision`. Возвращает `{ok:true}` при доказанном коммите или `{ok:false}` при конфликте; новое значение revision определяется хранилищем.
- Если запись имеет **неопределённый исход** (например, таймаут после коммита), адаптер должен отклонить Promise. Координатор **не повторяет** такие попытки: нужен повторный `read()` и примирение состояния.
- Упрощённая реализация `localStorage.getItem()` + `setItem()` **не является атомарным CAS** между вкладками. Подходящие варианты: `readwrite` транзакция IndexedDB по одному ключу на том же origin, серверное условие `If-Match`/ETag, транзакция базы данных. Chrome storage API без CAS требует дополнительного механизма.
- Все пишущие сущности, включая пресеты и прежние версии UI, должны уважать CAS; один внешний обходной writer снова создаёт риск потери данных.

**Пример подключения в хосте SOL:**

```js
const cas = createXodCasViewCoordinator({
  read: () => xodStorage.readDocumentWithRevision(),
  compareAndSwap: (expected, next) => xodStorage.commitIfRevision(expected, next)
});
const session = await cas.openView('youtube-main');
const table = mountYoutubeTable300(root, {
  ...options,
  view: session.view,
  onSaveView: session.onSaveView
});
// При уничтожении экрана:
table.destroy();
session.dispose();
```

- `session.onSaveView(view)` делает атомарную проверку **двух** ревизий: общий CAS всего документа и `data.viewRevisions[scope]` конкретного вида. Изменения разных scope после CAS-конфликта безопасно переигрываются на новом snapshot, изменения *одного* scope отклоняются `XOD_VIEW_CONFLICT`.
- `session.reload()` читает актуальную версию и возвращает `{view,revision}`, но **не меняет уже открытый компонент**: SOL должен предложить пользователю **обновить с сервера** либо **сохранить локальные изменения поверх новой ревизии**, затем заново смонтировать компонент или поддержать обновление вида. Никакого молчаливого overwrite.
- `session.dispose()` предотвращает старт ещё не начавшихся в очереди операций. Уже отправленный CAS отменить нельзя.
- `cas.transaction(syncPureMutator)` позволяет обновлять другие разделы (пресеты) в том же атомарном документе. Мутатор может повторяться после CAS-конфликта, поэтому не должен делать I/O, порождать случайные ID и иметь внешние побочные эффекты. Для `create preset` нужен **стабильный ID**, вычисленный до транзакции, и/или idempotency key, чтобы повтор после неизвестного коммита не создал дубликаты.
- Счётчики `viewRevisions` существуют отдельно от `views` и автоматически создаются при первой успешной записи. Для старых документов без этого свойства исходная версия каждого вида равна 0. При миграции все writers должны перейти на новую схему одновременно.

**Важно:** это **альтернатива/замена** координатора CHAT 08 при наличии настоящего CAS, а не второй уровень обёрток вокруг него. Не использовать CAS поверх отдельной очереди с устаревшим `read/write`.

## 6. Интеграция и риски

1. 🟩 SOL должен сначала определить настоящий тип хранилища. Если есть реальная атомарная транзакция/CAS, адаптировать её к указанному контракту и проверить результат на двух вкладках **того же браузерного origin**.
2. Не заменять JS таблицы. Сохранить исправления SOL (повтор поля сортировки/глубина фильтра) и пакеты CHAT 04/06/07 при необходимости.
3. Если два редактора меняют один вид, показать локальный конфликт; только пользователь решает, перезаписать ли чужие изменения. До решения сохранить локальный вид в UI, не теряя его.
4. После CAS внедрения протестировать перезапуск, ошибка сети **после возможного коммита**, разные вкладки и, если XOD sync поддерживается, разные устройства.
5. Для `presets` обеспечить idempotency: CH03 старый `{op:'create',name,view}` **не содержит operationId**, и повтор после неопределённой записи может создать дубликат. Это открытый риск, не решённый данным координирующим модулем.

**Итог:** CHAT 09 предлагает проверенный на симуляции алгоритм распределённой защиты. Без реального CAS SOL его использовать небезопасно; публичный компонент сохраняет прежние контракты.
