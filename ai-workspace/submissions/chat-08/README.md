# XOD · CHAT 08 — защита сохранения настроек между поверхностями YouTube

**Состояние:** 🟦 CHAT, `SOL_STATE=SLEEPING`, 21.11.2026. Готов автономный **референсный адаптер хранилища**, не изменение компонента. Фактическая локальная интеграция SOL отсутствует. Менять `main` запрещено.

## 1. Текущий шаг
`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.5. Текущий шаг · 🟦 CHAT — конкурентное сохранение вида между поверхностями.`

## 2. Найденный риск и воспроизведение
Исходные `saveView` в CHAT 04/07 последовательно отправляют `onSaveView` **только внутри одного экземпляра таблицы**. Когда два компонента используют один общий JSON-объект настроек, независимый асинхронный read→modify→write способен завершиться в обратном порядке. Последний завершившийся запрос перезаписывает снимок другого компонента, включая **другие ключи вида** или пресеты.

**Подтверждение:** сценарий 01 в `multi-surface-browser.html` демонстрирует потерю одного из двух видов на настоящем DOM с намеренно небезопасным адаптером. Node.js gate отдельно воспроизводит тот же случай. Это свойство наивного хост-адаптера; нельзя утверждать, что конкретное хранилище SOL неисправно, пока не проверены его код и тесты.

## 3. Референсное решение
`xod-view-store-coordinator.js` экспортирует `createXodViewStoreCoordinator({read,write})`; требует, чтобы `read()` возвращал JSON-объект, а `write(snapshot)` завершался только после реальной записи. Компонент и его публичный API **не изменяются**.

```js
const coordinator = createXodViewStoreCoordinator({
  read: () => xodSettings.read(),     // полный JSON-снимок
  write: snapshot => xodSettings.write(snapshot)
});
const a = mountYoutubeTable300(rootA, {
  ...configA, onSaveView: coordinator.bindView('youtube-main')
});
const b = mountYoutubeTable300(rootB, {
  ...configB, onSaveView: coordinator.bindView('youtube-sidebar')
});
// Для пресетов и других частей ТОГО ЖЕ документа хранилища:
await coordinator.transaction(draft => {
  draft.presets = nextPresets;
});
```

- **Одна очередь на физический JSON-документ**, с последовательностью read→clone→mutate→write.
- Снимок вида копируется при вызове; позднейшая мутация исходного аргумента не меняет сохранённый payload.
- Ошибка одной операции возвращается её вызывающему компоненту, но не блокирует последующие записи.
- `transaction(mutator)` позволяет сериализовать другие разделы документа (например пресеты), не перетирая новые изменения видов.
- Все новые объекты и операции остаются внутри выделенного адаптера; у таблицы сохраняются CHAT 04/06/07 контракты.

**Файлы пакета:** `xod-view-store-coordinator.js` — координирующий адаптер; `multi-surface-browser.html` — браузерный gate (5 проверок); `store-gate.js` — Node.js gate (9 проверок); `README.md` — инструкция. Браузерный gate ссылается на соседние файлы CHAT 07/08 и требует подключения рабочего JS CHAT 07 при исполнении в окружении SOL.

## 5. Ограничения безопасности и интеграции
1. **Единственный экземпляр координатора на один физический документ**, общий для всех поверхностей этого runtime. Если две независимые копии координатора пишут в один файл, гонка сохраняется.
2. **Между вкладками/браузерами/устройствами** одной очереди недостаточно: нужен CAS/revision/ETag в хранилище SOL, транзакционный сервер или собственный lock; нельзя обещать защиту cross-tab.
3. При одном `scope` последняя **вызванная** операция побеждает. Для гарантии порядка именно пользовательских действий между independently queued компонентами нужны ревизии/события от SOL; данный пакет их не изобретает.
4. `transaction` не защищает от постороннего кода XOD, который пишет тот же JSON в обход очереди; хост обязан направить **все** записи этого документа через один сериализатор.
5. Текущий адаптер — референсная основа, не готовый storage: `read/write` обязан безопасно обеспечивать реальную сохранность, ошибки, восстановление. В memory/localStorage тестах нет проверки настоящей персистенции.

## 6. Порядок действий SOL после пробуждения
1. Проверить фактический сериализатор XOD: возможно, реальные write-транзакции уже атомарны, и пакет нужен только как регрессионный тест.
2. Если поверхность имеет общий JSON и read-modify-write без глобального порядка — встроить **один coordinator** на соответствующий документ и подключить существующие `onSaveView` к `bindView(scope)`. Для `onChangePreset` предусмотреть операции через `transaction`, сохраняя его контракт полного списка.
3. Сначала сохранить исправления SOL (повтор полей сортировки/глубина фильтра), затем при необходимости применить CHAT 04, CHAT 06 и CHAT 07. Для CHAT 08 патча на JS таблицы **нет**.
4. Запустить `store-gate.js` (Node), `multi-surface-browser.html` (браузер с реальным компонентом), отдельные тесты XOD storage и перезапуск в Chrome/Edge; зафиксировать только фактически выполненное.
