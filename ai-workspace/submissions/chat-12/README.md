# XOD · CHAT 12 — защита пресетов от устаревших изменений из других вкладок

**Дата:** 2026-11-21. **Статус:** независимый референсный host-адаптер и тесты готовы в обычном CHAT, **не интегрировано** в локальную XOD SOL. Рабочая ветка `ai-workspace`, `main` не изменять; 🟩 SOL спит до явного сигнала 👤 ДИМЫ.

## 1. Текущий шаг

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.9. Текущий шаг · 🟦 CHAT — конфликтные rename/update/delete пресетов между вкладками.`

## 2. Выявленная ошибка в прежнем контракте CHAT 10

`createXodPresetIdempotencyAdapter` сериализует действия через **атомарный CAS общего JSON-документа**, но для `rename`, `update`, `delete` проверяет только ID пресета, а не ревизию, увиденную пользователем. Поэтому два редактора могут открыть один пресет, после чего более поздняя операция со старой вкладки молча перепишет новое имя/вид или удалит обновлённый пресет. Атомарность CAS сама по себе **не предотвращает** семантическую потерю пользовательских изменений. Тест 01 в `preset-version-gate.js` воспроизводит потерю с эквивалентным устаревшим мутатором (не выполняет исходный CHAT 10 файл непосредственно).

## 3. Решение и контракт

`xod-versioned-preset-sessions.js` экспортирует `createXodVersionedPresetSessions({read,transaction,makeId})`; возвращает `openSession()`. Хост должен использовать настоящий **атомарный** `transaction(syncMutator)` из CHAT 11 (или эквивалентный CAS) и `read()` **из того же источника данных**, возвращающий `{revision,data}`.

```js
const sessions = createXodVersionedPresetSessions({
  read: () => xodStorage.readWithRevision(),
  transaction: cas.transaction, // CHAT 11, только если реальный CAS
  makeId: () => crypto.randomUUID()
});
const session = await sessions.openSession();
const table = mountYoutubeTable300(root, {
  ...otherConfig,
  presets: session.presets,
  onChangePreset: session.onChangePreset,
  presetOperationIds: true // нужен CHAT 10 opt-in для create.operationId
});
// При уничтожении: table.destroy(); session.dispose();
// При конфликте: сохранить пользовательский локальный вид/имя, показать
// XOD_PRESET_CONFLICT с remotePreset, затем только по явному действию:
const latest = await session.reload(); // host remounts/rebinds UI with latest
```

**Компонент UI не изменяется.** Публичный `onChangePreset(command): Promise<full presets[]>` сохранён; ревизии не нужно добавлять в команду, поскольку отдельная session хранит исходные версии каждого ID.

- Для `rename`, `update`, `delete` проверяется `presetRevisions[id]`, полученная при открытии сессии. CAS-мутатор отклоняет устаревший запрос с `XOD_PRESET_CONFLICT` (expectedRevision, actualRevision, remotePreset), **не записывая ничего**. Редактирование других ID из разных вкладок объединяется после CAS-конфликта.
- При успешном изменении ревизия конкретного ID увеличивается. При удалении остаётся **tombstone** в `presetRevisions`, чтобы старые редакторы не приняли повторно использованный ID за новый. `makeId` не должен повторять когда-либо использованный ID.
- `create` требует `operationId` из CHAT 10 UI; receipt и пресет сохраняются **в одной** атомарной транзакции. Повтор с тем же ID после потерянного подтверждения не создаёт второй пресет. Изменение payload под тем же token запрещено.
- Если результат `rename/update/delete` неизвестен (например, ACK пропал **после** фактической записи), сессия блокирует новые изменения кодом `XOD_PRESET_RECONCILIATION_REQUIRED`, пока хост явно не вызовет `reload()` и не разрешит конфликт. Исключение: безопасный повтор **того же** `create.operationId` благодаря receipt; другие create блокируются.
- `dispose()` останавливает ещё не начатые операции, не отменяя уже отправленный CAS. Перезагрузка сессии обновляет baseline только по явному действию хоста, а не автоматически.
- `presetRevisions` у старых документов может отсутствовать: исходная ревизия равна 0; **все writers обязаны перейти на новый контракт одновременно**, иначе защита обходится.

## 5. Существенные ограничения

1. Без **действительно атомарного** CAS/transaction XOD хост-схема с `presetRevisions` не защищает данные. `localStorage.getItem` + `setItem` не является межвкладочным CAS; Node/Python тесты — симуляция, не доказательство реального storage.
2. Одноразовая `reload()` после неизвестного исхода может прочитать состояние раньше позднего коммита. Хосту нужен UX подтверждения/разрешения; нельзя молча терять несохранённое имя или вид. Для промышленной гарантии нужны операции и receipts с устойчивой идентификацией либо авторитетное решение об окончательности запроса.
3. Модуль — **альтернатива** неверсированному адаптеру CHAT 10 для хоста (сохранена идея idempotent create), а не параллельная запись через два разных адаптера. Другие писатели пресетов обязаны тоже уважать ревизии.
4. Список `presets` по завершении успешной операции содержит актуальные данные всего документа, но локальная сессия не обновляет baseline известных **чужих** ID автоматически. Это может дать консервативный конфликт (нужно reload), зато не допустит silent overwrite на устаревшем UI.
5. Настоящие Chrome/Edge на ПК пользователя, IndexedDB, персистентность после перезапуска и локальная интеграция SOL не проверены.
