# XOD · CHAT 07 — безопасное повторное монтирование YouTube-таблицы

**Дата:** 21.11.2026. **Исполнитель:** 🟦 CHAT. **Статус:** минимальный патч и браузерные тесты готовы; реальная интеграция SOL не выполнялась. Рабочая ветка `ai-workspace`; `main` не менять.

## 1. Текущий шаг

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.4. Текущий шаг · 🟦 CHAT — жизненный цикл DOM при remount.`

## 2. Подтверждённая ошибка

Если вызвать `mountYoutubeTable300(root,...)` дважды на одном DOM-контейнере без предварительного `destroy()` старого экземпляра, первый handle остаётся активным. Его последующее `destroy()` выполняет `root.replaceChildren()` и уничтожает **новую** таблицу. Кроме того, отложенные запросы сохранения первого экземпляра могут исполняться после повторного монтирования.

Репродуктор: `old=mount(root,cfg); current=mount(root,cfg); old.destroy();` — в CHAT 06 новая таблица исчезает. В CHAT 06 при `old.setGroup(); current=mount(root,cfg)` до обработки микрозадач старый `onSaveView` также может выполняться после замены.

## 3. Минимальное изменение

- Патч `chat06-to-chat07.patch` применяется **поверх CHAT 06**, а не вместо него. Добавляет локальный `WeakMap`, связывающий каждый root с текущим экземпляром.
- Новый mount после валидации контракта автоматически вызывает `previousInstance.destroy()`, тем самым предотвращает старые отложенные записи (совместно с CHAT 06).
- `destroy()` очищает DOM только у **текущего владельца** root. Старый handle не может уничтожить новую таблицу. Сохраняется корректное поведение класса `.yt-table300` на корне.
- Не добавляется ни одна новая глобальная функция, не меняются публичные аргументы, фильтры, сортировка, группировка, пресеты, адаптеры или хранилище.

**Важное условие:** патч защищает повторный mount одной и той же версии компонента (в рамках одного IIFE/WeakMap). Если хост динамически подменяет сам JavaScript-бандл другим экземпляром IIFE, между разными копиями модуля глобального общего реестра нет — интеграцию должен контролировать SOL.

## 5. Подключение SOL после пробуждения

1. Сначала сравнить актуальное управление lifecycle в XOD: если старый экземпляр гарантированно уничтожается до нового mount, дефект уже блокируется интегратором и патч **может оказаться не нужен**.
2. Если гарантий нет, перенести только изменения из `chat06-to-chat07.patch`. **Обязательная зависимость: CHAT 06** (защита `saveView` от записи после `destroy`); сохранить отдельные исправления SOL в сортировке и глубине фильтра.
3. Запустить `remount-lifecycle.html`, указав в нём фактический JS интегрированной XOD. На исходном CHAT 04 тест намеренно должен показывать FAIL; при корректном патче должен быть PASS 6/6. Добавить в регрессию 4/4 CHAT 06 и 37/37 CHAT 04.
4. Убедиться, что новая таблица сохраняет управление и записи после повторного mount, а старые callback не перезаписывают их состояния. Закрепить интеграционный результат в общем журнале.

**Сохраняемая граница:** этот пакет не исправляет возможные конфликты уже начатых запросов к внешнему storage; для них необходим контракт отмены/поколения на стороне SOL.
