# XOD · CHAT 10 — пресеты без дублирования после потерянного ответа

**Дата:** 21.11.2026 · **Исполнитель:** 🟦 CHAT · **Статус:** точечный патч + референсный хост-адаптер + тесты готовы, не интегрированы в локальную XOD SOL. Ветка `ai-workspace`; не менять `main`.

## 1. Текущий шаг

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.7. Текущий шаг · 🟦 CHAT — идемпотентность создания пресетов.`

## 2. Почему это нужно

Контракт CHAT 03 использует команду `{op:'create',name,view}`. Если host сохранил пресет, но ответ Promise потерялся, пользователь может нажать «Повторить запись пресета» и получить второй такой же пресет. Из одних только `name,view` невозможно определить, где сознательное создание дубликата, а где повтор той же операции. Следовательно, полностью исправить проблему **только внутри хранилища без изменения команды невозможно**.

CHAT 10 добавляет **строго опциональный** идентификатор логической операции `operationId`. Он сохраняется на повторе и отличается при новом успешном создании. Хост записывает receipt вместе с самим пресетом **в той же атомарной транзакции**.

## 3. Интеграция: три части и порядок

### 3.1. Патч UI, минимальное расширение команды

`chat07-to-chat10.patch` — минимальный diff к объединённому компоненту CHAT 07 (то есть CHAT 04 + CHAT 06 + CHAT 07). В `writePreset` добавлена генерация идентификатора **только для `create` и только когда `config.presetOperationIds===true`**.

- Без opt-in контракт CHAT 03 остаётся точным: `{op:'create',name,view}` без дополнительного поля.
- При opt-in команда создания становится `{op:'create',name,view,operationId}`. На кнопке «Повторить» тот же `operationId` сохраняется. Даже если пользователь снова нажал «Сохранить новый» после ошибки **с тем же именем и тем же видом**, используется исходный token; после успешного сохранения следующее намеренное создание того же пресета получает **новый** token.
- Генератор предпочитает `crypto.randomUUID()` (если браузер предоставляет), иначе использует fallback `Date.now` + `Math.random` для локального retry-token. Последний не криптографический: безопасность и уникальность для многоустройственного хранения должен оценить хост.
- Команды `update`, `rename`, `delete` не меняют форму. Фильтры, сортировка, группировка и прежние исправления SOL не затрагиваются.

### 3.2. Хостовый идемпотентный адаптер

`xod-preset-idempotency-adapter.js`: `createXodPresetIdempotencyAdapter({transaction,makeId})` возвращает функцию совместимую с `onChangePreset(command): Promise<[{id,name,view}]>`.

```js
const cas = createXodCasViewCoordinator({read, compareAndSwap}); // CHAT 09, только с РЕАЛЬНЫМ атомарным CAS
const onChangePreset = createXodPresetIdempotencyAdapter({
  transaction: cas.transaction,
  makeId: () => crypto.randomUUID()
});
mountYoutubeTable300(root, {
  ...config,
  presets: currentPresets,
  onChangePreset,
  presetOperationIds: true // включать только после готовности хоста
});
```

Адаптер хранит `draft.presets` и `draft.presetReceipts[operationId]={id,signature}` в **одном и том же атомарно записанном документе**. Если первый ответ потерялся, повторный вызов обнаруживает receipt и возвращает актуальный полный список без повторного создания. Если тот же token пришёл с другой полезной нагрузкой, результат — `XOD_OPERATION_ID_COLLISION` без изменений данных. ID пресета генерируется один раз **до** CAS-mutator, который может быть повторён после конфликта ревизий.

Если SOL использует иной формат своего storage, адаптировать алгоритм к его схеме. Сервис генерации ID должен выдавать уникальный ID между вкладками/устройствами. **Нельзя** сохранять receipts отдельно от пресетов, без атомарности. `localStorage.getItem` и `setItem` сами по себе не являются CAS.

### 3.3. Хранилище receipt и срок жизни

Для доказанной дедупликации после неизвестного коммита receipt должен пережить перезапуск и оставаться доступным до завершения окна возможных повторов. Референсный модуль **не чистит receipts**, чтобы не обещать защиту после их преждевременного удаления. Для длительной эксплуатации SOL должен определить окно хранения и политику безопасной очистки, явно признавая, что retry после очистки может снова создать дубликат.

## 6. Для SOL после сообщения о пробуждении

1. Проверить, как фактически создаются и сериализуются пресеты. Если сервер/хранилище уже имеет устойчивый operation ID — не дублировать реализацию, только добавить regression gate.
2. Если нет — подключить CAS или иную **атомарную** транзакцию для `presetReceipts + presets` (CHAT 09, если применим). Не использовать CHAT 10 adapter поверх неатомарного storage.
3. Перенести UI patch минимально, включить `presetOperationIds:true` только после готовности хоста; сохранить фильтры/сортировки/глубину и код SOL.
4. Протестировать фактическую ситуацию «committed, response lost» на настоящем хранилище; два вкладочных клиента с тем же token и разные token, восстановление после перезапуска, жизненный цикл и предел хранения receipts.
5. Если нынешний адаптер отклоняет неизвестные поля команды, **не включать opt-in**, пока он не научится принимать `operationId`.

**Граница:** клиентский token предотвращает тихую повторную отправку как новое создание только при сохранении того же token. Если пользователь после ошибки меняет название/состав вида, это **новое намерение** и новый token, а предыдущая операция может уже сохраниться. Для UX такого случая нужен отдельный механизм отмены/поиска незавершённых операций.
