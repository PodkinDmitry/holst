# XOD — канонический формат ответов

**Версия 3.8 · 23.11.2026 · строгая спецификация по запросу 👤 ДИМЫ.**  
**Цель:** минимизировать время чтения, когнитивную нагрузку и число действий пользователя. **Чат — изменения и решения; GitHub — полные результаты и рабочая память.**  
**Статус UX:** визуальная компоновка v3.2 (полные описания слева, пять вплотную стоящих метрик справа, CAPS/выступающая главная остановка, единая линия и адаптивный перенос) **утверждена пользователем 22.11.2026**. Версия 3.3 расширила операционный/измерительный протокол; версия 3.4 закрепляет автоматический выбор мини-панели или полной карты по §4.13, сохраняя утверждённый UX v3.2.
**Источник истины:** этот файл в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Новые прямые инструкции 👤 ДИМЫ имеют приоритет. Не создавать копии шаблона с другими названиями.

## 1. Показывать только новое

**Основной принцип — «дельта вместо полного отчёта».** Каждый содержательный ответ показывает, что изменилось **со времени предыдущего ответа**, а не пересказывает весь проект и прежние итерации. **Контекстная шапка обязательна в каждом ответе**: её краткое повторение нужно для ориентации и не считается запрещённым дублированием.

Порядок важности:
1. **Результат:** одна человеческая фраза о полезном изменении.
2. **Доказательство:** один показатель фактически выполненных проверок, если они были, либо точный статус «не проверено».
3. **Результат в GitHub:** одна-две ссылки на конкретный пакет и живой журнал, если запись выполнена.
4. **Ориентация:** текущий шаг, следующий шаг, нужное действие 👤 ДИМЫ.
5. **Подробности:** в GitHub или раскрываемом блоке, а не в основном потоке чтения.

Не повторять прежние показатели, лимиты, длинные технические детали, неизменившиеся статусы или сам план без необходимости. **Исключение XOD:** компактная мини-панель в конце рабочей сессии либо полная карта после принятого значимого шага/прямого запроса (§4.13); это не повод повторять остальные части отчёта. **Исключения:** всегда показывать контекстную шапку; для работы — кратко указывать текущий шаг и действие 👤 ДИМЫ. Существенный риск, требующий решения пользователя, **не прятать** в раскрываемые подробности.

## 2. Навигация и роли

Для содержательных задач XOD сохранять каскад **от стратегии к тактике**, минимум четыре уровня; номера этапов не переизобретать между ответами. **Путь принадлежности контекста** (§2.1) и **номер шага** — разные навигационные оси: не добавлять вымышленные уровни принадлежности ради четырёх уровней рабочего плана:

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.5. Сохранение`

- **Текущий шаг** указывать явно с номером и исполнителем в одном фиксированном месте отчёта: `1.1.1.5 · 🟦 CHAT`.
- **Следующий шаг** показывать отдельно, только когда он действительно отличается; назначать ему реального исполнителя. Не придумывать следующий номер при продолжении того же шага.
- Хронологические события внутри шага: `1.1.1.5.1`, `1.1.1.5.2`, `1.1.1.5.3`. Они обозначают события, **не** новые уровни стратегического плана.
- 🟦 **CHAT** — подготовка, тесты, патчи в период сна SOL либо по его подтверждённому делегированию; 🟩 **SOL** — главный оркестратор всей разработки XOD, включая стратегию, распределение работ, интеграцию и контроль; 🟪 **ASTRA** — архитектурная эскалация; 👤 **ДИМА** — пользователь.
- Не предполагать, что SOL проснулся, получил сообщение или увидел GitHub. До прямого сообщения 👤 ДИМЫ состояние SOL — `SLEEPING`. Лимиты приводить как *последние сообщённые*, не как текущий остаток.

### 2.1. Обязательная контекстная шапка — строгий стандарт 2.9

**Первой содержательной областью каждого ответа** должна быть контекстная шапка. Её три независимых поля:

- **ТИП КОНТЕКСТА** — что за объект обсуждается: `ПРОЕКТ`, `ПРОЦЕСС`, `ЗАДАЧА`, `ДОКУМЕНТ`, `ВОПРОС`, `ИССЛЕДОВАНИЕ`, `ТЕМА` или другой точный тип. Не называть всё подряд «темой». Выбирать один ведущий тип для текущего ответа, даже если объект связан с несколькими.
- **ЗАГОЛОВОК** — короткое **КОНКРЕТНОЕ НАЗВАНИЕ ТЕКУЩЕГО КОНТЕКСТА ЦЕЛИКОМ КАПСОМ**. Это главный визуальный ориентир. Не превращать весь текст ответа или все заголовки в капс. Не писать только `XOD · CHAT 08` вместо смысла ответа: идентификатор пакета, роль и статус — вторичные метаданные.
- **ПУТЬ ПРИНАДЛЕЖНОСТИ** — компактная иерархия реально известных родительских объектов, например `LIFE OS → XOD → Управление ИИ → Шаблон ответов`. Она показывает, где находится объект, но не является номером рабочего этапа; глубина определяется реальной структурой, а не фиксируется искусственно. При неясной принадлежности показать ближайший достоверный уровень и не выдумывать недостающие.

**Нормативный вид (без альтернативного порядка при поддержке компонентов):**

```text
ДОКУМЕНТ · ТЕКУЩИЙ КОНТЕКСТ
НАВИГАЦИЯ ПО КОНТЕКСТАМ ЧАТА
LIFE OS → XOD → Управление ИИ → Шаблон ответов
[КОНТЕКСТЫ ЧАТА · 3 ▾]  ← только кнопка раскрытия
```

В длинных ответах помещать шапку **внутрь одной внешней рамки** (§4), в коротких — показывать компактным текстом без обязательной рамки. В промежуточных сообщениях добавлять тип и заголовок к маркеру, но не разворачивать карту.

### 2.2. Карта контекстов — доступна всегда, содержимое только при раскрытии

**Последнее решение 👤 ДИМЫ:** в шапке постоянно видна только компактная точка доступа `КОНТЕКСТЫ ЧАТА · N ▾`; **список и описания контекстов скрыты до нажатия**. Это отменяет более ранний вариант «постоянно видимая карта». По умолчанию карта **закрыта**, не открывать её автоматически при смене контекста. Наведение без клика не должно самостоятельно раскрывать список. Если интерфейс поддерживает `popover`, использовать кликабельный `popover-trigger`; иначе нативное раскрытие (если поддерживается) или компактный текстовый аналог без ложных обещаний интерактивности.

Разделять:
1. **ЧАТ** — контейнер разговора; его название не ограничивает будущие контексты.
2. **КОНТЕКСТ** — устойчивый объект обсуждения с одним типом, названием и принадлежностью, например проект, документ или процесс.
3. **КАРТА ЧАТА** — оглавление всех **достоверно обнаруженных значимых контекстов** данного разговора, включая текущий; не список каждого сообщения и не копия внешней карты проекта.
4. **ШАГ** — позиция в выполнении работы внутри выбранного контекста; не равен теме ответа и не меняется только из-за смены темы.

**Правила ведения карты:**
- В раскрытом виде помечать текущий контекст `СЕЙЧАС` и, при наличии данных, `ОТЛОЖЕНО`, `ЗАВЕРШЕНО`, `В ДРУГОЙ ВЕТКЕ`. Не путать статус обсуждения со стадией реализации кода.
- Сначала пытаться отнести новый вопрос к уже существующему контексту; новый пункт создавать лишь для самостоятельного направления с возможностью продолжения. Не создавать «темы» для каждого уточнения.
- Если контекстов много, показывать компактные названия и группы (при необходимости 3–5 основных плюс раскрываемый остаток внутри карты). Не повторять в карте длинные описания и результаты прошлых шагов.
- При переключении темы менять **текущую шапку**, но не удалять предыдущие контексты из карты. Перенос в другую ветку отмечать **только по подтверждению**; не считать перенос завершением проекта.
- **Не выдумывать полный индекс**, когда часть истории недоступна: отражать только известные контексты и указывать ограничение охвата. `N` приводить только при достоверном подсчёте; иначе надпись без числа.
- Карта — **ориентир**, а не автоматическая система навигации к старым сообщениям: не изображать названия ссылками для перехода без реально доступных URL/действий.
- Не создавать новый файл-карту чата или параллельные канонические документы без прямого запроса; краткий индекс можно поддерживать непосредственно в контексте чата.

## 3. Промежуточные сообщения

У промежуточных сообщений должен быть явно **другой визуальный язык**, чем у финала: **ровно одна Markdown-цитата** с узнаваемым маркером, без общей финальной рамки. Состав строки фиксирован §4.3:

> **◌ ПРОМЕЖУТОЧНО · 🟦 CHAT · ДОКУМЕНТ: ШАБЛОН ОТВЕТОВ · 1.1.1.5**
>
> Подтверждена причина […]. Сейчас выполняю проверку […].

Отправлять только при появлении полезного факта, реального препятствия или существенной операции; не писать пустые обновления для видимости активности. Промежуточное сообщение — не финальный результат, не означает работу в фоне между ходами и не заменяет запись в GitHub.

## 4. Строгий макет ответов · версия 3.4

**Нормативный контракт, не свободные рекомендации.** Агенты используют одинаковые порядок, подписи, размеры, рамку и раскрытия. Меняется фактическое содержимое, но не макет. Режимы: **РАБОЧИЙ** (существенный результат, несколько операций/проверок/артефактов), **КРАТКИЙ** (простой ответ) и **ПРОМЕЖУТОЧНЫЙ** (§3, §4.3).

### 4.1. РАБОЧИЙ ответ: фиксированный порядок

1. **ШАПКА** — тип контекста, затем **конкретный смысловой заголовок ЦЕЛИКОМ КАПСОМ**, затем путь принадлежности. Идентификатор CHAT NN и роль вторичны, не заменяют заголовок.
2. **КАРТА ЧАТА** — один всегда видимый триггер `КОНТЕКСТЫ ЧАТА · N` (число только при достоверном подсчёте); при клике раскрывается поповер с достоверными контекстами и маркером `СЕЙЧАС`. **По умолчанию закрыта, от наведения не открывается.** Не показывать вторую карту в основном тексте.
3. **РАЗДЕЛИТЕЛЬ** — ровно один `<divider color="subtle"/>` между шапкой и результатом.
4. **РЕЗУЛЬТАТ** — ровно одна строка `**Результат:** [одна фраза]`, перед остальным содержимым. Не повторять вывод в цитатах и подвале.
5. **СОБЫТИЯ** — от нуля до трёх отдельных Markdown-цитат `<blockquote>` с хронологическими **новыми** фактами. Метка каждой: `**[ID шага] · Найдена проблема/Выполнено/Проверено/Опубликовано/Нужна проверка**`. Не придумывать события ради числа блоков. Указывать один агрегированный результат реально проведённых проверок, а не всё множество старых PASS.
6. **ССЫЛКИ** — до двух обычных ссылок, основной результат и/или живой журнал, только подтверждённые фактические адреса; не делать из них рекламные карточки или кнопки.
7. **РИСК** — одна открытая фраза, только если есть существенный риск, неопределённость или блокер. Риски, меняющие действия пользователя, **не скрывать** в popover.
8. **ВЫБОР ROADMAP ПО СОБЫТИЮ (§4.13)** — в финале каждой рабочей сессии XOD показывать мини-панель текущего шага: прогресс-бар, завершённость и четыре метрики (Work %, экономия CHAT %, часы, обоснованность %). После доказанного завершения значимого маршрутного подшага/чекпойнта или по прямому запросу пользователя показывать **полную дорожную карту §4.6 вместо мини-панели**. Не показывать обе сразу; не вставлять в промежуточные сообщения или простые нерелевантные ответы. Экспорт §4.7 — только по запросу, синхронизация — через GitHub §4.10.
9. **РАЗДЕЛИТЕЛЬ** — ровно один `<divider color="subtle"/>` перед подвалом.
10. **ПОДВАЛ** — фиксированные строки: Текущий шаг (ID, исполнитель, результат блока); Следующий шаг (если общая задача открыта, даже при том же ID; конкретная зависимость и исполнитель); 👤 ДИМА (действие/кнопка или узкое «действий не требуется» по §4.9). Не смешивать завершённую диагностику с открытым дефектом.
11. **ДЕЙСТВИЕ** — действующая кнопка только при реально необходимом следующем запуске/передаче; если всё уже опубликовано в GitHub и пользователя не нужно привлекать, дать ссылку без кнопки. Явно запрошенный полный экспорт §4.7 сохраняется.
12. **ДЕТАЛИ** — один заключительный popover технических подробностей по необходимости; нельзя прятать туда обязательные решения или критические риски.

**Фиксированные настройки внешнего вида (при поддержке DIL):** одна и только одна рамка `<box border radius="xl" padding={3} gap={3}>`, нейтральный фон. Шапка `<box gap={1}>`. Тип `<text size="2xs" color="secondary" weight="medium">`. Заголовок `<title size="lg">` **капсом**. Путь `<text size="xs" color="secondary">`. Триггер карты `<text size="xs" underline>` с иконками `list-tree` и `chevron-down` при доступности. Для раскрытия `<popover showOnHover={false}>`. Разделители только `<divider color="subtle"/>`. Основной текст стандартного размера. Не менять визуальную иерархию по вкусу агента, не добавлять цветные плашки, лишние заголовки, карусели и блоки-обёртки. **Исключение:** вложенный аккордеон и структурированная таблица внутри блока §4.6, когда эта панель применима; внешняя рамка и два внешних разделителя остаются неизменными.

**Стандартные подписи (печатать дословно):** `ТЕКУЩИЙ КОНТЕКСТ`, `КОНТЕКСТЫ ЧАТА`, `Результат:`, `Текущий шаг:`, `Следующий шаг:`, `👤 ДИМА:`, `ТЕХНИЧЕСКИЕ ПОДРОБНОСТИ`. Не использовать варианты «ТЕМА ОТВЕТА», «ИТОГ», «КАРТА ТЕМ», «ДАЛЬШЕ», «РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ».

**Нормы краткости:** шапка — 3 короткие строки; результат — одна фраза; каждая цитата — обычно не больше двух коротких смысловых предложений; ссылки — максимум две; подвал — 2–3 строки. Расширять лишь для необходимой точности, безопасности или по запросу.

### 4.2. КРАТКИЙ ответ

Сохранять **тот же тип/заголовок КАПСОМ/путь и один триггер карты**, затем одно-два предложения ответа. Нет искусственных цитат, хронологии, номера шага или подвала без рабочего процесса. На узком экране или для однофразового ответа общая рамка необязательна, но порядок и подписи не меняются.

### 4.3. ПРОМЕЖУТОЧНЫЙ ответ

Только одна Markdown-цитата, без полной финальной рамки, карты и подвала: `◌ ПРОМЕЖУТОЧНО · [РОЛЬ] · [ТИП: ЗАГОЛОВОК КАПСОМ] · [ШАГ ЕСЛИ ЕСТЬ]`. Финальный ответ снова содержит полную шапку и карту. Не выдавать статус за готовый результат.

### 4.4. Fallback без богатого интерфейса

Тот же порядок в Markdown: `ТИП · ТЕКУЩИЙ КОНТЕКСТ` → `# ЗАГОЛОВОК КАПСОМ` → путь → `КОНТЕКСТЫ ЧАТА` → результат → события (если есть) → ссылки → подвал. Не рисовать неработающий «раскрываемый» элемент. Если реального раскрытия нет, написать короткую текстовую ссылку на карту или перечислить достоверные контексты лишь по запросу.

### 4.5. Границы и исключения

- Риски потери данных и необходимые решения всегда видимы; дизайн не должен скрывать существенное.
- Утверждать `Проверено`, `Опубликовано`, `Интегрировано` только по доказательствам (§6).
- **Продолжение разработки:** при `SOL_STATE=SLEEPING` кнопка только по §7. При `AWAKE` переход SOL только по §10 и без same-chat кнопки.
- Диаграммы/таблицы/изображения вместо стандартных абзацев — по содержательной необходимости. Нормативные исключения: мини-панель с прогресс-баром §4.13 в конце рабочей сессии XOD; полная карта §4.6 при принятом значимом шаге или прямом запросе. Простые ответы не перегружать.
- GitHub сам по себе не распространяет изменения на чаты, которые не перечитали инструкцию (§8).


### 4.6. «ДО ТОЧКИ Б»: единая панель дорожной карты, бюджета, экономии CHAT и времени · версия 3.4

**Назначение.** В одной компактной встроенной панели совместить карту уже пройденных шагов, полный остающийся путь до **последней утверждённой точки Б**, статус каждого этапа, расходы недельного лимита Work, экономию от бесплатного CHAT и ориентировочную активную трудоёмкость. Панель показывать в рабочих ответах по многоэтапной разработке XOD, при обсуждении ресурса/прогресса/роадмапа и по прямому запросу. Не выводить на короткие справочные и нерелевантные ответы. В обычном отчёте показывать только свернутый триггер, чтобы карта не перегружала чтение. **До вывода и копирования проверять предметную полноту по §4.8.**

**Нормативная компоновка (не popover).**

1. **Главный триггер-аккордеон** на одну или максимум две компактные строки: **«ДО ТОЧКИ Б · ЗАВЕРШЕНО [X%]»**; ниже при необходимости **«Work […]% · экономия CHAT […]% · время […] ч»**. При недостаточной доказательной базе: **«ЗАВЕРШЕНО: Н/Д»** (либо доказанный интервал/граница с покрытием). **Прогресс и расход Work — независимые метрики** (§4.11). Запрещено подменять прогресс красивым неподтверждённым числом. Клик раскрывает содержимое **в потоке ответа на доступную ширину**, а не во всплывающем окошке; иконка меняется chevron-down/chevron-up. По умолчанию главный блок закрыт, **кроме ответа, в котором пользователь прямо попросил показать карту** — тогда допустимо открыть его сразу.
2. **Внутри строго два независимых вложенных аккордеона**, по умолчанию оба закрыты: **«ИСТОРИЯ · [достоверное количество записей]»** и **«ТЕКУЩЕЕ И БУДУЩЕЕ · [этапы/подшаги, если подсчитаны]»**. Пользователь может открыть каждый отдельно или оба одновременно. Внешнее раскрытие не заставляет раскрывать историю. Вложенные блоки — часть одной панели, не отдельные полностраничные отчёты.
3. **ИСТОРИЯ:** хронология реально известных работ до текущей контрольной точки; фиксировать выполненные шаги, выпущенные/тестовые сборки, результаты проверок, проверенные и отложенные пакеты CHAT. **Отдельно обозначать:** подготовлено → протестировано на стенде → интегрировано в XOD → проверено в целевой среде → принято пользователем. Например, у XOD CHAT 01–03 интегрированы в тесты 09–11, CHAT 04–12 проверены/оценены, но **их полный пакет не интегрирован автоматически**; группировка SOL присутствует в тесте 12; тест 13 исправил и проверил резервирование настроек расширения. Это примеры на основании журнала 21.11.2026, **не вечные статусы**.
4. **ТЕКУЩЕЕ И БУДУЩЕЕ:** показывать всю подтверждённую последовательность **до самой дальней утверждённой точки Б** (в действующем плане XOD 3.0 → 3.0b → 3.1 → 3.2 → 3.3 → 3.4 → 3.5 → 3.6), а не обрывать на ближайшей итерации. **Без вкладок выбора точки Б**: интересующий этап уже виден в едином маршруте. Актуализировать конечную версию только по изменению плана, не расширять дорожную карту вымыслом.
5. **Одна непрерывная хронологическая линия с заметной иерархией:** каждый этап и подшаг остаётся отдельной последовательной остановкой (3.0 → 3.0.1 → ... → 3.0b → ...), соединённой линией. **Главный этап:** название ВЕРХНИМ РЕГИСТРОМ, жирное, немного крупнее и **на 8–12 px левее подшагов**, чтобы «выступать» из линии как дорожный указатель; этап не является контейнером. **Подшаг:** обычный регистр/шрифт, плотнее и **+8–12 px вправо относительно уровня этапа**. Соединительная линия непрерывна, в том числе через границу этапов. Иерархия — типографическая, а последовательность единая; история аналогична.
6. **Шесть полей, ПОЛНОЕ ОПИСАНИЕ при приоритете текстовой колонки:** «Шаг / описание / статус | Завершено % | Work % | Экономия CHAT % | Время, ч | Точность оценки %». **Нельзя выбрасывать, сокращать до одного названия, обрезать `truncate/maxLines` или скрывать значимую пользовательскую/каноническую детализацию ради ширины метрик.** Под ID и именем шага оставлять полноценное многострочное описание существа работ, условия приёмки и актуального статуса из базового плана; если исходный текст длинный, разрешён перенос строк и, при необходимости, раскрытие самого описания без потери в полном экспорте. **На широком экране** название и описание получают ВСЁ оставшееся пространство (`flex: 1`), а справа стоит **один узкий блок из 5 метрик строго рядом друг с другом**, с фиксированными или content-sized компактными ширинами (ориентир 50–70 px каждая, общий блок около 280–330 px), `gap` около 2–6 px, **без пяти одинаковых растянутых колонок на всю ширину**. Заголовки метрик образуют тот же компактный блок. **На узком экране**, где одновременно текст и метрики не помещаются, переносить **весь компактный блок метрик ниже полного текстового описания**, не менять шесть полей и их порядок. Не создавать горизонтальный scroll, fixed minWidth и не жертвовать описанием; релизы CAPS+BOLD и на 8–12 px левее подшагов, хронологическая линия непрерывна.
7. **Строка этапа агрегирует подшаги, не добавляется повторно к сумме**. Итог до точки Б, если он вычислим, показывается один раз внизу будущей секции (**общая завершённость %, Work %, чистая экономия CHAT %, активные часы**), затем метка **«ТОЧКА Б · [последняя версия/критерий приёмки]»**. Исторический расход учитывать отдельно и не суммировать в **оставшуюся** стоимость работы. Если у части шагов нет данных, выводить частичную оценку с покрытием или **«НЕ ОЦЕНЕНО»**, а не достраивать недостающие числа.

**Метрики — обязательные правила достоверности.**

- **Work % — основная метрика.** Процент от **полного недельного лимита выбранного платного режима**, не от текущего остатка и не количество токенов. Для длинного маршрута сумма может быть больше 100%: это **эквивалент одного полного недельного лимита, накопленный за несколько периодов**, а не утверждение о доступной квоте в данный момент. Другие режимы/модели не считать взаимозаменяемыми.
- Строго различать **ФАКТ** (измеренный расход и известные статусы), **БЮДЖЕТ** (выделенный потолок, например ранее 8% на 3.0, 5% на 3.0b и 5% резерв, на момент соответствующей ревизии), **ПРОГНОЗ** (обоснованная калибровкой оценка) и **ГИПОТЕЗУ** (условная модель). Не называть бюджет фактическим расходом или прогнозом завершения. Не превращать относительные числа расхода токенов напрямую в проценты Plus/Work без калибровки. Числа из прошлого отчёта, включая условные 59–99% и оценку экономии CHAT, **не переносить как установленный факт**.
- **Экономия CHAT %** — **чистая** разница платного Work с делегированием и без, с учётом поручения, проверки, адаптации, интеграции и дополнительных исправлений SOL. Если прямых измерений нет, можно дать явно маркированный сценарный диапазон и допущение; при недостаточных основаниях — **«н/д»**. Не трактовать бесплатный CHAT как автоматически 100% экономии; допускается отрицательная экономия.
- **Время, ч** — прошлое только из подтверждённых отметок времени/длительности, будущее — приблизительные диапазоны активной работы по конкретным подшагам, обязательно с уровнем уверенности. При недостатке информации указывать **«н/д»**; не придумывать затраченное историческое время. Не смешивать активные часы ИИ, календарное ожидание, ручную работу 👤 ДИМЫ и длительность тестового прогона (например, 30-минутный тест не равен общей трудоёмкости приёмки).
- У всех числовых столбцов **только символ %**, не сокращение «п.п.»; для неоднозначных значений раскрывать смысл формулировкой «% полного недельного лимита». Различать **0% (подтверждённый ноль)** и **«—»/«н/д» (нет данных)**; не заполнять выдуманными нулями пустые значения. Суммы должны арифметически сходиться; если интервалы получены разными способами, явно объяснить, почему их нельзя складывать.
- Данные для примера XOD читать из **актуального** журнала **ai-workspace/handoffs/work-resume-latest.md**, особенно последних оперативных разделов, и утверждённого плана итераций. Старые сборки и оценки не являются текущими автоматически; сверять стадии по проверкам. Если исходники недоступны, показывать границы охвата, не выдавать демонстрацию за живую телеметрию.

**Сценарные численные значения и «Точность оценки %» v3.0.** Если прямые замеры отсутствуют, но можно явно задать метод и источник, показывать **помеченный условный интервал** вместо сплошного н/д; не выдавать его за подтверждённую продуктовую завершённость. Подтверждённые acceptance-gate проценты продолжают подчиняться §4.11: неизвестный критерий не равен нулю или PASS. Сценарная доля завершённости строится отдельно по промежуточным результатам и имеет индекс точности. Для Work допустима только открытая условная модель с указанием некалиброванного коэффициента; **никакого прямого пересчёта токенов или часов в расход квоты без пометки о гипотезе**. Экономия CHAT — чистый условный результат после передач, ревью, исправлений и вызовов Work; старые срезы лимитов нельзя называть текущим остатком.

**Формула аудируемой колонки:** Точность оценки % = 15×Scope + 15×Source + 20×SourceTests + 25×TargetE2E + 15×MeasuredTimeQuota + 10×CalibratedForecast. Каждый фактор от 0 до 1, должен иметь источник или честный ноль; максимум 100%. Индекс измеряет **обеспеченность предпосылок доказательствами**, **НЕ** реальную статистическую вероятность точного попадания в прогноз. При недостатке замеров времени/Work числовой сценарий существенно менее надёжен; после 2–3 сопоставимых фактических задач нужно считать эмпирическую ошибку и перекалибровать модель. Проценты точности на каждой строке нельзя интерпретировать как достоверность Work-прогноза отдельно от общей модели.
**Приоритет смысловой полноты v3.2:** предыдущая попытка сделать карту компактнее удалением описаний и статусов признана 👤 ДИМОЙ неверной. Приоритет использования ширины: (1) **полное название, описание и текущий статус в левой расширяющейся области**, (2) **узкий собранный блок чисел справа**, (3) плотный вертикальный ритм. Нельзя заменять детали источника на короткие заголовки без доступного раскрытия; сохранять утверждённые подпункты (в частности подробности 3.0 скорости, надёжности, расширения, переименования; список багов 3.0b и назначение остальных релизов). **Нельзя путать визуальную компактность с сокращением содержания.** Если реальная доступная ширина недостаточна, переносить числовой блок целиком на следующую строку, оставляя названия и описания видимыми.

**Обязательный анализ повышения точности v3.1.** Под расчётами добавлять компактный **план измерений, ранжированный по ценности информации**: (I) сверить фактический код/два локальных SOL-fix, собрать для 3.0 реальные приёмочные gates и воспроизвести открытый FAIL1265; (II) запускать реальные Chrome/Edge/IndexedDB/Drive/многовкладочные/краш-тесты и хранить PASS/FAIL с источником; (III) для каждого действительно необходимого Work-блока фиксировать модель/effort, долю недельного и 5h лимита до/после, активные часы, затраты на review/retry и итоговые тесты; (IV) калибровать трудоёмкость и бюджет на 2–3 первых сопоставимых пакетах предварительно, лучше на 10–20 завершённых пакетах проверять фактическую ошибку и покрытие интервала. **Приоритет — измерения, которые одновременно закрывают релизный gate**, а не отдельные дорогостоящие эксперименты. История внешних запросов не доказывает Work-расход. **Индекс 0–100 из §4.6 — только полнота свидетельств; назвать его эмпирической «точностью прогноза» нельзя.** Желательно отображать отдельные индексы по каждой метрике в деталях (прогресс, время, Work, экономия), потому что общий процент, например 17%, маскирует нулевую калибровку Work-прогноза. Не обещать точные будущие проценты индекса: условные максимальные добавки по его определению составляют до +25 пунктов за target E2E, до +15 за замеры времени/квоты и до +10 за калибровку; реально они зависят от покрытия всех 37 работ. Сначала улучшать точность близкого релиза 3.0, затем дальних этапов, не выдавая локальное доказательство 3.0 за +25 пунктов к глобальной модели 3.0–3.6.

**Визуальный контракт.** При DIL использовать **box с нейтральной тонкой рамкой + pressable, управляемый DIL.useState**, с двумя вложенными независимыми pressable/box для разделов; раскрываемая часть находится сразу под собственным триггером. Рядом с триггером нужна отдельная кнопка «КОПИРОВАТЬ ВСЁ», не зависящая от состояния раскрытий и экспортирующая **все строки** (§4.7). Для карты не использовать popover (он подходит для коротких «ТЕХНИЧЕСКИХ ПОДРОБНОСТЕЙ», но не для длинной таблицы). Оставить обычные размеры шрифта, небольшие вторичные подписи, одну табличную сетку в каждой секции, нейтральные иконки; никакие декоративные цветные badge не нужны. **Два разделителя §4.1 относятся к основному отчёту; внутри раскрытой панели допустимы собственные локальные разделители.** При отсутствии интерактивного UI использовать нативный работающий аккордеон либо краткий текстовый эквивалент, без имитации нажатий.

**Проверка перед отправкой:** 8 релизов + 37 подшагов на одной хронологической линии с соединениями; релизы CAPS и немного левее; **у каждой строки сохранены полные описания и содержательный статус, сверенный с исходным планом**; правые пять метрик визуально сжаты в соседний компактный блок и не растянуты на всю доступную ширину; при нехватке места переносится именно весь блок метрик под полное описание, не наоборот; нет горизонтального скролла или усечения текста; метрики/точность/источники и весь полный экспорт сохраняются.


### 4.7. КРИТИЧЕСКОЕ ПРАВИЛО: полный перенос данных через буфер · версия 3.4

**Проблема, обнаруженная 21.11.2026:** копирование свернутой панели XOD передало заголовки и агрегаты, но **потеряло 18 строк истории, 8 этапов, 37 подшагов и показатели каждой строки**. Принцип: **достоверная переносимость равноправна корректности информации и визуализации**; интерфейс без полного экспорта не принимать как готовый.

**Ограничение платформы:** обычное Ctrl+C, выделение и встроенная команда копирования ответа не обязаны включать скрытые условные ветки. Поведение нативного копирования ChatGPT агент не контролирует и не может утверждать, что все закрытые данные сохранены. Предусмотренный способ — явный обработчик кнопки, вызывающий **GenUI.copy(fullMarkdown)** при клике. Это не автоматическое копирование и не независимая проверка системного буфера.

**Норматив для любого информационно насыщенного интерактивного ответа** (аккордеоны, таблицы, карточки, переключаемые виды, документы):

1. **Единый полный источник данных** для UI и экспорта: полный набор структур с идентификаторами, порядком, уровнями, содержимым, статусами, всеми числовыми значениями, единицами, примечаниями, решениями, ограничениями, основаниями и ссылками. **Нельзя** собирать текст копии из реально отрисованного на экране фрагмента. Раскрытия, вкладки, фильтры и свернутые состояния **не должны удалять сведения из экспорта**. Если значимые сведения содержатся в тексте ответа вне панели, включать их в полную копию.
2. **При экспорте, прямо запрошенном пользователем, доступная кнопка «КОПИРОВАТЬ ВСЁ»** рядом с главным триггером, **вне условий видимости**. По прямому нажатию вызывает **GenUI.copy(fullMarkdown)**. Экспорт — самодостаточный читаемый **Markdown** со всей историей, текущим и будущим планом, статусами и **шестью колонками** §4.6 (шаг/статус, завершённость %, Work %, экономия CHAT %, часы, точность оценки %), включая прогресс всего маршрута, каждого чекпойнта и подшага, веса, методику расчёта и покрытие данных (§4.11). Не путать с **GenUI.issueNewTurn**, который отправляет только в текущий чат.
3. **Паспорт экспорта** в начале: название, принадлежность, дата среза, версия/ссылки на источник, точка Б, смысл чисел (факт, бюджет, прогноз, гипотеза), ожидаемые **вычисленные по массивам** счётчики: «история=N; этапы=M; подшаги=K». В самом конце — обязательная строка **«КОНЕЦ ПОЛНОГО ЭКСПОРТА | история=N | этапы=M | подшаги=K»**. Она помогает обнаружить обрезание, но не является криптографической проверкой.
4. **Превентивная самопроверка до выдачи:** числа записей в исходных массивах, рендере и копии должны совпадать; должны присутствовать все идентификаторы, первые и последние строки, поля, источники, пояснения, единицы и завершающая метка. Проверить соответствие итогов подшагам, отсутствие дубликатов и непреднамеренных пропусков; не заменять неизвестные показатели нулём. При несовпадении **исправлять автоматически**, а не предъявлять пользователю неполную кнопку как работающую.
5. **Приёмка другим чатом:** после вставки первым делом сверить паспорт, реальные количества записей и завершающую строку, наличие разделов и полей; при несоответствии **не продолжать работу по частичной копии**. Если доступен канонический источник — перечитать его; иначе запросить корректный полный экспорт.
6. **Fallback:** если действие копирования недоступно, не рисовать фиктивную кнопку; предоставить полный обычный текст или проверенный источник с прямым указанием ограничения. Если лимит копирования не позволяет один текст, тогда и только тогда — пронумерованные части с общей ведомостью. Не заставлять пользователя вручную раскрывать все ветки и собирать фрагменты.
7. **Тест переноса:** сценарий «все тоглы закрыты → кнопка экспорта → вставка в другой чат → проверка полноты» должен быть предусмотрен заранее. Статическая проверка массива и текста **не равна** проверке фактического содержимого ОС-буфера. Без фактического подтверждения из принимающего чата нельзя утверждать, что перенос был проверен end-to-end.

**Минимальная схема DIL (не данные XOD):** один массив records; и закрытая/открытая визуализация, и текст экспорта получают данные из records. Экспорт строится независимо от состояния открытости; кнопка доступна всегда. Пример обработчика: **onClick={() => GenUI.copy(fullMarkdown)}**. Не использовать DOM, navigator.clipboard или несуществующий host action.

**Неприемлемый исход:** красивый интерфейс, который переносит лишь видимые заголовки и теряет скрытые записи. **Приоритет сохранности выше оформления.**


### 4.8. Межчатовая реконструкция: полное содержание ДО копирования · версия 3.4

Результат для каждого шага: сохранён / добавлен / изменён / удалён с причиной. Законные причины: завершён, перенесён, заменён, объединён, отменён по решению пользователя. Прежние **8% + 5% + 5%** из §25 отменены. После подтверждённого недельного сброса условные верхние лимиты **45% на 3.0 / 30% на 3.0b / 25% резерв** — бюджеты, не стоимость всего маршрута. Если предыдущий снимок доступен, сохранить их **лишь как явно помеченные некалиброванные гипотезы с датой, низкой уверенностью и методикой**, либо осознанно пересчитать, объяснив изменённые допущения. **Нельзя молча заменить все часы на н/д**, выдавая новый сокращённый документ за полное воспроизведение. Нельзя смешивать старый сценарный прогноз с новыми 3%/2%/5% в одну согласованную сумму. Если сам предыдущий снимок недоступен — честно отметить невозможность восстановления прежних значений.
6. **Корректный паспорт:** для истории считать **группы G / уникальные работы H / всего строк G+H**; для предстоящего **релизные этапы E / подшаги S / всего строк E+S**. Строки-группы не равны отдельным сделанным задачам. История «24 строки» (5 групп и 19 дочерних) не доказывает появления 6 новых работ относительно прежних 18 исторических записей. Контроль расхода Work относить к бюджетной информации, а не в счётчик завершённых инженерных работ.

Если источник не получен или расхождения не устранены — **не называть копию «ПОЛНЫЙ ЭКСПОРТ»** и не скрывать ограничения за контрольной строкой. Пытаться исправить автоматически по доступным источникам до привлечения пользователя.
8. **Представление результата:** в чате достаточно короткой дельты и исправленной интерактивной панели. Не заставлять пользователя вручную сопоставлять две длинные карты и не создавать новый канонический файл без выбора пользователя.

**Критерий успеха:** сохранены утверждённые содержание и допущения; сведения актуализированы по новым источникам; полнота входной модели проверена; лишь затем проверена целостность переданного текста. **Самосогласованный экспорт неполной модели — критический дефект.**


### 4.9. Обязательные работающие кнопки, непрерывность и точные статусы · версия 3.4

**Требование пользователя:** в каждом финальном отчёте о выполненной работе готовить кнопку **только когда она выполняет необходимое действие**, а не копирует канон, доступный в GitHub; пользователь не должен вручную писать «продолжай» или составлять поручение другому агенту. Завершать весь доступный связанный объём в текущем ходе, а не дробить работу ради кнопок. Обычный чат **не продолжает самостоятельно после завершения ответа**: кнопка запускает ровно одно новое сообщение только после нажатия.

**Матрица выбора одной основной кнопки (сверху вниз):**
1. **Следующая безопасная задача разрешена в этом же чате; текущая GitHub-блокировка свободна; полномочия подтверждены** → кнопка «Продолжить [конкретный блок]» с действием GenUI.issueNewTurn(fullNextPrompt). Промпт самодостаточен: канонический журнал, задача, критерии, повторная проверка владельца, блокировки, тестов и рисков. Нажатие не переключает модель и не запускает бессрочный фон.
2. **Нужен другой чат, SOL, браузерный исполнитель или Work** → если адресат имеет доступ к GitHub, он сам читает актуальные AGENTS.md, журнал, протоколы и артефакты. **Не копировать весь контекст пользователем.** Когда другой чат требуется отдельно запустить, допустима лишь короткая команда запуска со ссылкой на канон. Полный GenUI.copy(fullHandoff) — только если адресат не имеет доступа к источникам или пользователь явно просит полный перенос; GenUI.issueNewTurn не открывает другой чат.
3. **Чужая живая GitHub lease, нет назначения или требуется разрешение** → не запускать конкурентную разработку. Если результат сохранён в GitHub, дать ссылку, не копировать тот же материал. Буфер — резерв при отсутствии прямого доступа или явно запрошенном переносе.
4. **Действительно нечего запускать** → если результат уже записан в GitHub, достаточно прямой ссылки, **кнопка копирования не нужна**. При отдельном запросе на перенос данных использовать «КОПИРОВАТЬ ВСЁ» по §4.7; не дублировать её.
5. **Действия интерфейса недоступны** → без фиктивных кнопок; дать самодостаточный готовый текст для копирования и обозначить ограничение. Не перегружать промежуточные сообщения и не относящиеся к задачам краткие ответы кнопками без смысла.

**Раздельная отчётность.** Обязательно различать (A) статус завершённого *локального блока* и (B) статус *основной проблемы/релиза*. Подвал «Текущий шаг» обозначает локально завершённое, «Следующий шаг» — незавершённую зависимость **даже с тем же ID**, но с конкретным иным результатом и исполнителем. Фраза «действий не требуется» допустима для завершённого блока, но **если следующий шаг требует нового пользовательского хода**, сразу подписывать конкретную кнопку; иначе такая фраза вводит в заблуждение относительно непрерывности. Не писать, что агент продолжает работать в фоне без действующей автоматизации.

**Пример проверки CHAT 14 по журналу §32 (21.11.2026):** диагностический Python-модуль и тестовый патч подготовлены; 12/12 Python unit, 5/5 Node isolation, Python syntax и build неизменного Test 13 PASS. Пять файлов пакета опубликованы, их соответствие проверено в предыдущем чате. Это **не доказательство исправления браузерной ошибки**. Исходный FAIL tests/app_regression.py:1265 остаётся OPEN; полный Chrome/Edge E2E не выполнен. Гипотеза о конкурентном saveNow()/updatedAt не подтверждена в реальном браузере. Не смешивать PASS сборки и закрытие release gate. Печатать результаты компактно: «Проверено: Python 12/12, Node 5/5, build PASS; E2E не запускался», а не оформлять три отдельных гигантских заголовка с числами.

**Правильный следующий gate:** разрешённый браузерный запуск с диагностическим JSON-path diff, затем узкое исправление лишь по реальному diff. Перед выдачей кнопки проверять свежие SOL_STATE, WORK_EXECUTION, NEXT_AGENT, реальное поручение и chat-run-lock.json. Например, при живой блокировке CHAT 15 нельзя кнопкой начинать параллельный CHAT 16. Ссылки GitHub должны быть чистыми, без добавленных рекламных utm-параметров; две ссылки выводить раздельно. Не менять приватный исходник Test 13 и не публиковать его в публичный репозиторий без решения владельца.

**Чек перед ответом:** кнопка действительно имеет onClick и допустимый host action, соответствует направлению этого/другого чата, текст самодостаточен, нет ложной фоновой непрерывности, нет обхода lock, не сообщается о завершённой приёмке при открытой проблеме; не утверждать нажатие или доставку без доказательства.


### 4.10. Прямое чтение GitHub вместо копирования · версия 3.4

**Решение пользователя от 21.11.2026:** когда проектный агент имеет доступ к репозиторию, **он самостоятельно восстанавливает состояние из GitHub**. Вручную переносить стандарт и журнал между чатами нет необходимости. Это правило **имеет приоритет** над старыми фразами о «обязательной кнопке копирования» в §§4.9, 7 и 10 и над примерами прежних версий.

**Алгоритм нового хода:** агент читает актуальные AGENTS.md, канонический формат, рабочий журнал, план, назначение исполнителя, GitHub lock и нужные артефакты. История прежнего чата и присланные цитаты не заменяют фактическое чтение. После существенной работы публикует результат в существующем источнике, перепроверяет сохранение. Другой агент увидит это **лишь при собственном последующем чтении**, не по автоматической рассылке.

**Не смешивать назначение буфера:**
- **Синхронизация проекта между агентами:** GitHub-first, никакой копии по умолчанию.
- **Передача данных по явному запросу пользователя** (например, полный экспорт интерактивной панели): действующая «КОПИРОВАТЬ ВСЁ» сохраняется по §4.7 и обязана включать скрытые данные.
- **Необходимость запустить отдельный чат/Work:** если невозможно отправить ему сообщение напрямую, допустима короткая команда запуска с указанием прочитать GitHub; полные документы не копировать. Кнопку копирования этой команды использовать лишь если она реально экономит пользовательские действия.
- **Нет доступа к GitHub / источник недоступен:** тогда полный самодостаточный экспорт через GenUI.copy или обычный текст — резерв, с явным указанием ограничений.

**Критерий QA:** перед каждой кнопкой копирования спросить: «может ли адресат сам прочитать опубликованный материал?». Если да, **удалить лишнюю кнопку**, оставив прямую ссылку и корректный статус. Если следующий ход не требуется, действие пользователя — отсутствует. Никаких обещаний фонового продолжения без отдельного механизма запуска.

### 4.11. Три уровня завершённости roadmap · версия 3.4

**Утверждённое изменение от 22.11.2026; уточнение v3.0.** Расчёт завершённости ведётся по трём уровням (вся дорога → релизы → подшаги), но **все отдельные релизы и подшаги показываются одной линейной хронологией с соединительными линиями, без визуальной вложенности**. Общий процент — в главном триггере и итоге, каждый релиз и подшаг — в собственной строке; две секции раскрываются независимо.

**Визуальная иерархия (норматив):**

```text
ДО ТОЧКИ Б · XOD 3.6 · ЗАВЕРШЕНО [общий %]
  ИСТОРИЯ · [подтверждённые ранее работы; без отдельного двойного счёта]
  ТЕКУЩЕЕ И БУДУЩЕЕ
    ● 3.0 Фундамент             Завершено [чекпойнт %]
    │
    ● 3.0.1 Скорость            Завершено [подшаг %]
    │
    ● 3.0.2 Надёжность          Завершено [подшаг %]
    │
    ● ... 3.0.5                Завершено [подшаг %]
    │
    ● 3.0b Критические ошибки  Завершено [чекпойнт %]
    │
    ● 3.0b.1 ...               Завершено [подшаг %]
    │
    ● ... 3.6.5                Завершено [подшаг %]
  ИТОГО ДО Б                    Завершено [тот же общий %]
```

**Расчёт по доказательствам — снизу вверх:**

1. **Подшаг:** фиксировать конкретные *критерии приёмки* (acceptance gates), их веса и результаты. Завершённость = 100 × сумма весов **подтверждённо пройденных** критериев / сумма весов всех критериев. Для частично выполненного критерия включать отдельные проверяемые дочерние критерии, а не назначать субъективные 30/70%. Если работа в самом деле не начата и это подтверждено — 0%; если состояния критериев неизвестны — **н/д** или доказанный диапазон, не притворяться нулём. **100% подшага** — только когда выполнены все *обязательные* критерии в целевой среде и нужная приёмка, не по автономному стенду.
2. **Главный чекпойнт:** взвешенное среднее завершённости **его подшагов**. Веса — согласованные доли трудоёмкости/объёма (предпочтительно по принятому плану); без обоснованных весов допустима **явно подписанная ориентировочная метрика «по числу подшагов, равные веса»**, не выдаваемая за точную готовность релиза. Критичный непройденный интеграционный или safety gate препятствует статусу «принят» и **100% чекпойнта**, независимо от количества PASS.
3. **Вся дорога A → Б:** взвешенное среднее **чекпойнтов**, учитывающее их разные размеры. Предпочитать согласованные веса/трудоёмкость; если их нет, резервный объективно воспроизводимый ориентир — суммировать веса *подшагов* всех этапов с одинаковым весом каждой единицы и обозначить **«приблизительно, по количеству подшагов»**. **Не усреднять проценты восьми релизов без указания весов**, если размеры релизов различаются. Период расчёта: от утверждённой стартовой точки A до последней утверждённой Б; фиксировать дату и версию плана.
4. **Неполные данные:** неизвестные критерии и подшаги не выбрасывать из знаменателя и не приравнивать к 0%. При известной части вывести доказанный **интервал минимально–максимально возможного прогресса** с покрытием исходных весов; если покрытие слишком мало — «н/д» с указанием пробела. При полной доказательной базе вывести одно число с методом. Округлять до целых %, если более тонкая точность не подтверждена; 0% и 100% использовать только при соответствующем доказательстве.
5. **История не входит повторно:** подтверждённые прошлые изменения зачисляются в завершённость **только соответствующих подшагов актуального маршрута**, если реально интегрированы и удовлетворяют их gate. CHAT-пакет, проверенный на модельном Node/HTML стенде, но не интегрированный в Test 13/не принятый SOL, **не равен** готовому релизу; нельзя добавлять 18 исторических записей поверх 37 подшагов в общий знаменатель. Перенос/изменение scope требует новой версии baseline и объяснения изменения показателя.
6. **Отдельные метрики:** «Завершено %» — подтверждённый gate либо отдельно обозначенная условная оценка; «Work %» — факт, бюджет или гипотеза (не смешивать); «Экономия CHAT %» — чистая разница включая проверку и ревью; «Время, ч» — активная трудоёмкость; «Точность оценки %» — индекс покрытия источниками и тестами, а не статистическая гарантия. Source-only PASS не равен принятому продукту.

**Структура данных:** каждый подшаг содержит id, stageId, criteria[] (вес, статус, источник, среда), progressPct или progressRange, hoursRange, workRange, savingsRange, accuracyIndex, evidenceFlags, estimateClass (факт/бюджет/сценарий), scopeVersion. Этап и весь маршрут агрегируют подшаги, не считаются вторично; порядок отрисовки не меняет весов.

**Проверка (обязательный гейт):** все обязательные подшаги из утверждённого плана существуют; у каждого процента есть прослеживаемые критерии и источник; сумма весов нормирована; неизвестные не посчитаны как нулевые или выполненные; parent = корректная агрегация children; глобальный процент совпадает в заголовке и итоговой строке; нет двойного учёта истории; никакой открытый критический FAIL не превращён в 100%; копирование всех закрытых разделов сохраняет проценты и метод. Если расчёт невозможен — **н/д лучше выдуманного процента**.

### 4.12. CHAT-PLAN → CHAT-EXEC: планирование, измерения, допуск сильных моделей · версия 3.4

Это ориентиры бюджетирования, не гарантии будущего расхода. **🟩 SOL** как стратегический владелец/интегратор не означает постоянное использование дорогой Sol-модели. Если задача упирается в браузер или Windows checkout, нужна подходящая среда/оператор, а не априори Astra.

**Внедрённые измерения:** действующий инструмент `ai-workspace/tools/xod-metrics.py` (`--self-test`, `--empty-template`, `--input`, `--output`) принимает ссылки на проверенные acceptance gates, относительные Work snapshots по одной модели и одной квотной эпохе, а также завершённые сравнимые задачи; считает подтверждённый нижний прогресс и верхнюю границу, отдельно `target_e2e` от mock/source, фактические квотные дельты при доказанных before/after, предварительные ошибки/покрытие интервалов после ≥3 испытаний и индекс обеспеченности данными. **Он НЕ получает автоматически Usage UI, не доказывает истинность строк evidence_ref и не публикует приватные входные данные**. Снимок после reset или без достоверной пары → UNKNOWN; число тестов на Node VM не закрывает E2E. Отчёт размещать в действующем §31 журнала с датой, scope и доказательствами, без нового самостоятельного реестра.

**План повышения качества прогнозов:** сначала измерить реальные acceptance gates XOD 3.0, исправить root-cause `app_regression.py:1265` в хосте; во время действительно необходимых Work/GUI-сеансов фиксировать before/after % 5h+week по модели, reset, активное время, попытки, ревью; после 2–3 сопоставимых завершённых задач предварительно откалибровать квоту/часы, после ~10–20 — эмпирически измерять отклонение и coverage прогнозного интервала. Не запускать дорогой Work отдельно только ради статистики. Условный индекс из §4.6 — покрытие доказательствами, а не процент вероятности верного прогноза. Не повышать точность 3.6 из-за проверки только 3.0.

**Утверждённый макет:** единая вертикальная хронология и соединения; **релиз заглавными буквами и левее подшагов**; значимые подробные описания и статусы полностью остаются слева; **пять метрик плотно сгруппированы справа** в ~280–330 px с gap 2–6 px, без пяти равномерно растянутых пустых колонок; на узкой ширине весь блок чисел переносится на следующую строку, описание никогда не урезается. ### 4.13. Автоматический показ roadmap: мини-панель в рабочей сессии, полная карта после значимого шага · версия 3.4

**Прямое утверждение 👤 ДИМЫ 22.11.2026:** «в конце каждой рабочей сессии показывай мини-панель текущего шага, а после завершения значимого шага и по моему запросу — полную дорожную карту». Это обязательное правило отображения для итоговых рабочих сообщений XOD в CHAT-PLAN, CHAT-EXEC, SOL. Новых ходов, автоматических уведомлений и фоновой работы правило не создаёт.

**Три режима — ровно один на ответ:**

1. **ПОЛНАЯ КАРТА** при прямом запросе всей дорожной карты либо в том рабочем ходе, где **доказанно принят значимый маршрутный шаг**: утверждённый подшаг XOD 3.x.y завершён и прошёл обязательные целевые интеграционные/приёмочные проверки; релизный чекпойнт принят; изменилась официальная конечная точка Б или объём маршрута. Простая публикация автономного патча, синтетические тесты, успешная сборка, диагностический пакет, оформление или документ без релизной приёмки **не означают** завершение маршрутного подшага. Полная карта строго по §4.6: утверждённая компоновка UX v3.2, независимые аккордеоны истории/будущего, все содержательные описания, непрерывная линия, пять компактных метрик справа, а на узких экранах метрики переносятся ниже описания. Полная карта в этом ответе **заменяет мини-панель**, не дублирует её.
2. **МИНИ-ПАНЕЛЬ** во всех остальных **финальных рабочих отчётах XOD**, включая частичные результаты, подготовленные патчи, открытые тесты, блокировки и делегирование. Помещать в конце ответа после результата, риска и следующего действия. Показывать именно **текущий маршрутный подшаг**; если работа только про документацию/операционный процесс — пометка «операционный шаг; продуктовый маршрут не изменился», не приписывать себе новую степень готовности.
3. **БЕЗ ПАНЕЛИ** для коротких справочных ответов, промежуточных сообщений и других тем вне XOD. Не рисовать пустую декоративную визуализацию.

**Мини-панель: один компактный нейтральный блок, три строки и при необходимости четвёртая.**
- **Шапка:** версия XOD, ID шага, короткое название, реальный статус и граница проверки. Разделять локальный результат агента VERIFIED и статус продуктового маршрута OPEN/ACCEPTED.
- **Прогресс-бар:** «Завершено: X% / X–Y% / н/д» и подпись **ФАКТ / СЦЕНАРИЙ / НЕИЗВЕСТНО**. Закрашивать как факт только долю, доказанную принятыми критериями. Если интервал сценарный — показывать отдельный контур/нейтральную полосу возможного прогресса, **не закрашивать сценарный верхний предел как выполненный факт**. Для н/д — пустая полоса; нулевой прогресс не выдумывать.
- **Четыре метрики только этого шага:** Work % (с единицей полного недельного лимита и типом факт/бюджет/сценарий), чистая экономия CHAT %, активные часы, **обоснованность %** (индекс §4.6, а не вероятность верного прогноза). Данные брать из источников, отсутствие показывать как н/д. Компактная группа без широких промежутков; на узком экране переносить весь блок, не урезать название.
- **Далее:** одна короткая реальная зависимость, только если нужна для ориентации и не дублирует уже видимое действие. Не показывать историю, все 37 подпунктов и общую смету в мини-панели.

**Источники:** свежий GitHub-журнал и выданный маршрутный ID → подтверждённые acceptance gates и реальные проверки → исходный план → сценарная таблица с датой и оговоркой. Не вычислять завершённость из расходов Work, количества патчей или Node PASS; не называть прошлые квотные снимки текущими.

**Контроль перед отправкой:** запрошена полная карта? Если нет, есть ли новое подтверждённое принятие значимого маршрутного подшага/чекпойнта именно сейчас? Если да — полная. Иначе это финал рабочей сессии XOD? Если да — мини. Иначе — без панели. **Не показывать два режима сразу**, не заявлять E2E по source-only PASS, не терять полные данные при явно запрошенном экспорте (§4.7).

### 4.14. Непрерывность пользовательского пути и устранение «слепых переходов» · v3.5

**Источник:** прямые наблюдения 👤 ДИМЫ 22.11.2026 после Windows BROWSER-001: около 3 минут мигающего курсора без этапа/признака работы; неясность, нужен ли ещё приватный Test13 ZIP локально; значимые инструкции были только в README; Comodo заблокировал запуск; диалог/консоль после выбора архива и/или после «Нажмите любую клавишу» закрывался, пользователь не видел явного успешного/неуспешного исхода и не знал, что ждать `safe_summary.json`. Пользователь также дважды выбирал разные файлы. **Фактический итог Windows browser E2E / root cause `app_regression.py:1265` остаётся UNKNOWN**, пока реальный `safe_summary.json` не прочитан. Эти UX-события — свидетельство сбоя коммуникации, а **не** доказательство успешного либо неуспешного браузерного теста.

**Глобально применимый HAO-принцип (кандидат для CORE в существующем HAO Control Center, не отдельный новый реестр):** «В каждый момент делегированного действия человек должен понимать: *что сейчас выполняется, ожидается ли действие от него, как выглядит нормальное завершение, где появится результат, что делать при сбое*. По умолчанию строить сквозной путь без необходимости читать README, угадывать имена файлов, повторять запуск или искать скрытый результат. ИИ несёт ответственность за явные переходы и обратную связь, а не перекладывает их на пользователя». **Эта формулировка действует как правило проекта XOD в настоящем протоколе; нельзя утверждать, что она автоматически внесена в глобальные Custom Instructions или активирована во всех независимых чатах.** Актуальные HAO Library JSON/HTML — отдельный источник, защищённый от дублирующей несанкционированной перезаписи.

**Норматив для CHAT-PLAN/CHAT-EXEC/Work-инструментов, Windows `.cmd`/Python UI и любых выдаваемых пользователю многошаговых действий:**

1. **До запуска — один активный маршрут:** в чате дать **короткую последовательность подшагов с ожидаемым результатом и следующим действием**, в том же месте, где находится кнопка/ссылка запуска. Для каждого реально необходимого входа: точное имя, **файл или папка**, откуда взять, требуется ли скачивание на устройство; назвать дополнительный README и его роль («необязательная подробная инструкция»). По умолчанию одна основная кнопка с названием, из которого за 2 секунды ясно **что происходит и что делать**, без лишних декоративных кнопок. Не перенаправлять человека читать README для выполнения основного сценария.
2. **Во время выполнения — статус сразу и при задержках:** перед тяжёлой инициализацией показывать заголовок/ID и этап `Шаг k/N · Проверяю архив ...`, затем маркировать переходы (`подготовка → preflight → тест → результат`), короткий периодический heartbeat `Проверка продолжается: ...` во время длительного безмолвного ожидания. Не обещать точное время без измерения; работающий процесс нельзя изображать зависшим курсором. Если прогресс не измерим, показать *неопределённый, но живой* статус и текущее условие ожидания.
3. **После каждого этапа — явный переход:** статус `ГОТОВО / ВЫПОЛНЯЕТСЯ / ТРЕБУЕТ ДЕЙСТВИЯ / БЛОКИРОВАНО / ОШИБКА`, затем **один следующий шаг**, доступный на том же экране. Не заставлять пользователя определять по факту закрытия окна, выполнено ли задание; отсутствие вывода или преждевременное исчезновение окна — дефект пользовательского опыта. При CLI до закрытия показать итог, точный путь результата, что прикрепить/передать, и что произойдёт после клавиши.
4. **Выходной артефакт — заранее объявлен:** до запуска назвать **точное ожидаемое имя** (`safe_summary.json`), местоположение по умолчанию и пример, как его найти. После запуска показать **фактически** созданный путь, наличие файла и успех/отказ записи. При неуспехе не говорить «результат готов»; создать безопасный диагностический статус/лог при возможности, а если недоступно — показать точную понятную причину.
5. **Антивирус/SmartScreen/политики — безопасная обработка:** заранее обозначить возможность блокировки Comodo и иных защит, не советовать отключать антивирус, обходить политики, выдавать неизвестный скрипт за безопасный, массово добавлять исключения. При блокировке пометка `BLOCKED_SECURITY`, предложить просмотреть конкретное событие защитника и проверить происхождение/хеш файла; при необходимости сделать более прозрачный, подписанный/доверенный безопасный способ. Без подтверждённого разрешения пользователя не продолжать за блокировку.
6. **Ошибки без повторного труда:** повторный запуск должен отличать `уже созданы входы/выходы`, не требовать повторного выбора источника при безопасной сохранённой валидации, не терять причину прошлого сбоя. При неизвестном исходе сначала **проверить уже созданный отчёт/лог**, и лишь затем решать нужен ли повтор. ИИ не назначает человеку повторную работу «на всякий случай».
7. **Коммуникация в чате = встроенный навигатор:** для задач вне чата показывать компактный stepper с состояниями `готово / сейчас / дальше / заблокировано`, не только большую дорожную карту XOD. При каждом ожидании человека явно назвать результат предыдущего подшага и единственный следующий; не пересказывать целиком README. После пользовательского сообщения о непонимании сначала **диагностировать существующий результат**, затем менять инструмент; не требовать полного повторения задачи.
8. **UX acceptance перед передачей пользователю:** проверять сценарии `чистый запуск`, `долгое ожидание`, `отсутствие архива`, `не тот файл`, `нет зависимостей`, `Comodo/политика блокирует`, `вывод уже создан`, `ошибка при выполнении`, `успех и возврат отчёта`. **Реальная Windows UX-проверка отдельно от Linux/unit и source-backed VM.** Критерии: нет немаркированной длительной тишины, неизвестного пути результата, внезапного закрытия без статуса, зависимости от README в нормальном сценарии, лишних ручных повторов и опасных советов по обходу защиты. Не заявлять реальные Windows проверки без фактического запуска.

**Приоритизация исправлений:** исправлять не каждую формальную неровность интерфейса, а участки с высокой когнитивной ценой: повторный запуск, скрытый результат, неопределённый статус, чтение README ради базовой инструкции, сомнения об антивирусе, ручной выбор файла без явно указанного типа/пути. Предпочтительный показатель UX — число незапланированных решений и повторов пользователя на один **доказанно завершённый** результат. Время ожидания учитывать вместе с ясностью обратной связи; если процесс длится долго, это не делает его неработающим при понятном статусе.

**Область немедленного применения:** в следующих ответах CHAT-PLAN и заданиях CHAT-EXEC, включая BROWSER-001. **Не считать действующий Windows kit исправленным:** его корректировка и реальный Windows acceptance пока не выполнены. Данный раздел — утверждённое поведенческое правило и критерии, а не факт обновления запускающего кода.

### 4.15. Один исполнитель, проверяемая длительность CHAT, премиальная квота и незавершённые решения · v3.7

**Прямое утверждение пользователя 22.11.2026. Приоритет перед процедурными примерами обязательного CHAT-PLAN → CHAT-EXEC → SOL из §§4.12 и 7 (они остаются опциональным инструментом, но не обязательным маршрутом).** Источник требований — AGENTS.md ACTIVE override и автономный протокол v1.4. Роли сохраняют смысл, но по умолчанию **один доступный исполнитель** самостоятельно доводит работу до проверенной готовой сборки или точного препятствия; пользователь не диспетчер. Не отображать планирования, передачу задания и заполнение журнала как результат продукта. Не создавать дополнительные панели, регистры, документы и автоматические reminders.

**Контрольный результат и способ сообщения:**
1. В финальном рабочем ответе первым показывать **готовый проверенный результат**, что тестировано, что ещё открыто, ссылку на каноническое изменение. Обещание следующей сессии и запрос на передачу в отдельный чат не являются результатом. Если невозможно завершить из-за отсутствующего доступа, указывать точно какое действие/среда недоступны и что уже проверено.
2. **Ограничение времени обычного CHAT неизвестно**: наблюдения пользователя около 6 и 8 минут не доказывают универсального жёсткого лимита. Не вводить принудительную остановку «5 минут + 1 минута», не рассчитывать количество чатов по часам инженерной работы; прежняя оценка 4–7 запусков до ближайшего 3.0 не обоснована и снимается как количественный ориентир. Продолжать работу в одном ходе настолько, насколько позволяют реальные инструменты; фиксировать wall-clock начала/конца и прерывание лишь при их наблюдении. Длинные проверки выносить в детерминированные скрипты вне платного reasoning. Отделять **время ответа / инструментальное время / часы инженера / ручные действия**. Для проверки готового локального devkit доступен реально протестированный офлайн-инструмент `ai-workspace/tools/xod-cycle.py`, но без собственной AI-генерации кода и без автоматической целевой приёмки.
3. Бюджет платных вызовов: текущий **0% недельного остатка — сообщение пользователя, а не доступ к UI**; `>10%` возможен только узкий обоснованный call, `5–10%` премиальная операция только по прямому разрешению, `<=5%` некритичная работа прекращается, `0%` новые платные вызовы запрещены, `UNKNOWN` перед долгим вызовом нужно проверить. Доказательная пара before/after week и 5h, режим/модель, потолок, stop-loss и резерв релиза; отсутствие данных → **н/д**, не выдумывать достигнутую экономию. Нет платформенного автоматического механизма прекращения чужого Work — не обещать его.
4. **Незавершённые согласования показывать в содержательных ответах, даже если пользователь переходит к другой теме проекта:** короткий блок в конце, только реально важное и открытое. Статусы: `PENDING_APPROVAL` — нужно решение пользователя (обязательно предупредить до ухода в новую тему), `APPROVED_NOT_PUBLISHED` — уже утверждено, ожидает записи, `PUBLISHED_NOT_EXECUTED` — записано, но не реализовано, `BLOCKED` — точное препятствие, `DONE` — убрать из блока после проверки. Не напоминать о завершённом; не требовать повторного согласования утверждённого. Если другой чат не читал GitHub — не приписывать ему получение сообщения или знания. Принцип используется **ответами в чате**, не таймером, календарём или отдельной автоматизацией.
5. **Канонический roadmap по §§4.6–4.8, 4.13 не упрощать из-за экономии времени:** строго 8 релизов, 37 подшагов с полными описаниями, единая вертикальная ось, пять компактных метрик справа, история/будущее в независимых раскрытиях, полное копирование без потери данных. Новые оценки: остаток 3.0 = 9–23 активных инженерных ч, резерв 5–10 ч; полный остаток 3.0–3.6 = 218–459 ч, с резервом 223–469 ч; низкая уверенность. Проценты Work/экономии/готовности не пересчитывать без новых доказательств. Правило показа: мини-панель для рабочих финалов, полная карта при прямом запросе/значимом утверждённом milestone.
6. **Визуальный блок открытых решений** не делать огромным аккордеоном: максимум несколько строк с ID/статусом/следующим владельцем, только по необходимости. Если решения нет — блок не показывать. Текущая роль SOL как исторического владельца архитектуры **не означает доступную модель** после исчерпания квоты. Если вопрос о выпуске не решён, запись `XOD_RELEASE=OPEN` остаётся открытой без повторной просьбы предоставить уже выполненные проверки.

**Проверка v3.7:** сначала готовый результат, затем источник, затем реальное действие пользователя (только если неизбежно), затем компактные открытые вопросы. Проверять, что советы не предлагают пользователя диспетчером нескольких сессий, не требуют SOL при 0% квоты и не подменяют готовую сборку промежуточными документами.



### 4.16. Автономный триггерный режим и визуальный прогресс-бар с доказательствами на каждом уровне · v3.8 (23.11.2026)

**Прямое новое требование 👤 ДИМЫ; действует для каждого рабочего ответа A/B и координатора.** Название режима — **«автономный триггерный режим»**: каждый ручной клик `Продолжить` запускает в текущем чате полный доступный цикл; между кликами обычный CHAT не выполняет самостоятельной работы. `GenUI.issueNewTurn` может возобновлять только *текущий* CHAT; другой CHAT запустить этой кнопкой нельзя. Главный управляющий — текущий CHAT-координатор XOD; optional Work/Codex только ограниченный исполнитель без автономного изменения плана/интеграции, с подтверждённым бюджетом и явным пользовательским запуском. Полный технический протокол — `xod-autonomous-worker.md` §0.6. Это утверждение новее исторического SOL-takeover §10.

**Базовое визуальное требование:** в каждом ответе, где агент реально занят XOD, показывать **путь из 5 уровней**, с открытыми текущими критериями, и **прогресс-бар текущей задачи**, причём он должен сообщать *проверяемое продвижение к готовому результату*, а не объём затраченных усилий. Рекомендуемый минимально читаемый вид:

```text
XOD → 3.0 (релиз: PASS 2 / 7 gates; OPEN ≠ PASS)
  → A (поток: milestones 1/3 подтверждены)
    → A1 (веха: сохранность данных)
      → TASK-A-017 (конкретный неизменный task_id, 3/5 критериев)
        [██████░░░░] 60%   было 40% → стало 60%   Δ +20 п.п.
        ✓ C1 source FAIL reproduced · доказательство
        ✓ C2 исправление current source · commit SHA
        ✓ C3 source-backed tests · runner/result
        ○ C4 end-to-end integration test · NOT_RUN
        ○ C5 rollback/regression · NOT_RUN
      Следующее действие: C4; владелец A; blocker: cloud runner
```

**Это только пример панели и процента, НЕ текущие реальные значения XOD.** В настоящем проекте уровень 1 — релиз/текущая важная цель, уровень 2 — ответственный поток, уровень 3 — milestone, уровень 4 — stable task, уровень 5 — фиксированные acceptance criteria. Для сложных задач критерии могут иметь ссылку на доказательную таблицу в текущем журнале, но все активные критерии (PASS/FAIL/NOT_RUN) и путь уровней должны быть видны, не скрыты за придуманным средним %.

**Строгое правило расчёта:**
1. До работ зафиксировать `task_id`, критерии C1…Cn, их веса (равные по умолчанию; если неравные — объяснить заранее) и gate-class: `source`, `build`, `browser`, `storage`, `integration`, `release`.
2. Зачесть процент ТОЛЬКО за исполненный, проверенный критерий с `commit SHA + test runner/result` или равноценным доказательством; `Task % = 100 * verified_PASS_weight / fixed_initial_criterion_weight`. `Δ` = процент текущего доказанного чекпоинта минус предыдущий доказанный чекпоинт **того же** `task_id`. Не приписывать 20% за запуск тестов, создание TODO, сам факт commit, найденный баг или ещё одну новой task.
3. На родительских узлах не усреднять дочерние проценты без отдельной зафиксированной модели: релиз показывает `accepted gates / all gates` и типы блокеров. `SOURCE_ONLY_PASS` не даёт бонус к browser/integration/release gates. `build PASS` на старой базе 2.24 не засчитывать как 3.0 integrated candidate.
4. Добавленные по ходу работы подпункты обозначать `NEW/OUT_OF_BASELINE` и причину, **не менять задним числом знаменатель ради красивого числа**. При обоснованной перепланировке показывать `старый scope → новый scope`, остаток и корректировку; если PASS инвалидирован изменением API/базы, уменьшать показатель с пометкой `EVIDENCE_INVALIDATED`.
5. Если не существует стабильных проверяемых критериев — показатель `н/д`, по фактическим gate состояния `PASS/FAIL/NOT_RUN/BLOCKED`. Строго запрещены иллюстративные проценты вроде «55% на глаз» без явно отмеченной иллюстрации. Процент и bar должны совпадать визуально.
6. Если `Δ=0` за последний триггер, **пометить «ПРОГРЕСС СТОИТ»**, перечислить созданные задачи/пробы и почему они не приблизили acceptance. Два последовательных `Δ=0` → на следующем ходу обязательно пересмотреть гипотезу, инструменты/доступность, критический путь и возможность однократной помощи пользователя вместо бесконечного дробления задач. `Δ=0` при намеренной диагностике не является позором, но скрывать его нельзя.
7. Указать подтверждённый `PRIVATE_BRANCH_HEAD`, gate/status `PUBLISHED/VERIFIED/INTEGRATED/ACCEPTED`, следующий владелец, что блокирует и что выбрано следующим. Мини-панель для обычных рабочих ходов, полная вложенная панель по запросу пользователя. Сохранять ранее утверждённую полную карту **8 релизов / 37 подшагов** и её пять метрик отдельно от этого доказательного progress bar.
8. **Антислепое планирование:** перед массовой работой проверить доступный целевой исходник, checkout/GitHub permissions, runnable toolchain, CI/browser/data gates и дешевейшее снятие препятствия. Если private source отсутствует — исследовать перенос source в доступный private GitHub **до** серии source-only задач. Пользовательская ручная операция допустима, когда её одноразовая стоимость меньше многократного обхода. Не использовать отсутствие Windows/Test13 как blocker, если точный current source доступен в приватном GitHub и облачный runner может выполнить задачу.

**Формат финального состояния:** в коротком ответе 1–2 строки полезного завершённого результата → прогресс-бар текущей задачи с `до/после/Δ` → проверенные конкретные критерии и риски → при необходимости один next trigger для текущего чата. В длинных сессиях полный путь 5 уровней всегда доступен, а пользователю не нужно изучать длинный GitHub-журнал. При отсутствии результата не подменять его статусом «почитал файлы»; показывать фактический blocker и альтернативный маршрут.

## 6. Точность статусов и проверок

- **Подготовлено:** код/патч написан, без утверждения, что он протестирован.
- **Проверено:** фактически выполнены тесты; указать среду и результат, обычно одной агрегированной цифрой.
- **Опубликовано:** записано в GitHub; «проверено после публикации» — только если файл перечитан.
- **Интегрировано:** действительно работает в локальной XOD, после её регрессионной проверки, а не только в автономном стенде Chromium или имитации storage.
- **Передано SOL:** создан доступный для будущего чтения журнал/пакет; не равно «SOL увидел» или «SOL принял».
- **Утверждено 👤 ДИМОЙ:** только по его явному решению.
- **Текущие лимиты, модель, пробуждение, фон:** ничего не приписывать без данных.
- **Межчатовый перенос (§4.7–4.8):** сначала сверить семантическую полноту плана, актуальный журнал и прежний снимок; только затем проверять полный экспорт в буфер. Согласованные счётчики усечённой модели не являются доказательством полноты.
- Не выдумывать пути и не называть непроверенные проверки выполненными.

## 7. Продолжение XOD одним нажатием — с учётом актуального цикла

Это ранее принятое правило, расширенное §4.9. В рабочем чате XOD показывать кнопку «Продолжить XOD · GPT-6 High» только когда новый блок CHAT **разрешён** по актуальному журналу, подтверждённому поручению и свободной GitHub lease. Допустимые случаи: SOL_STATE=SLEEPING и автономность в пределах протокола; либо SOL_STATE=AWAKE + WORK_EXECUTION=COMPLETED + NEXT_AGENT=CHAT при прямом поручении пользователя или явном делегировании SOL. При SOL Work STARTED/RUNNING, чужом lock или отсутствии назначения — **не создавать** кнопку конкурентной разработки. Предпочитать самостоятельное чтение GitHub (§4.10); копировать только нужную команду запуска при реальной необходимости.

По нажатию GenUI.issueNewTurn отправляет **один** самодостаточный следующий запрос в **этот чат**, с обязанностью ещё раз прочитать канон, статус и lock перед записью. Это не переключение модели, не автоматическое фоновое продолжение и не запуск другого чата. Для другого чата не использовать действие отправки в этот чат: адресат при новом вызове сам читает GitHub. Если отдельный запуск необходим, допустима короткая команда; полный буфер — только резерв по §4.10. В чате изменения стандарта не запускать самостоятельную разработку и не предлагать копировать уже опубликованный канон.

## 10. Пробуждение Work: SOL возвращается как руководитель, не как исполнитель интеграционного поручения

**Норматив:** `AGENTS.md`, `ai-workspace/protocols/xod-autonomous-worker.md` §4 и `ai-workspace/handoffs/work-resume-latest.md` §24. При сообщении 👤 ДИМЫ, что Work доступен, нельзя автоматически делать очередное задание SOL «интегрировать CHAT 04–12», даже если это заметная техническая задолженность. Эта работа — только возможная подзадача, выбираемая SOL после восстановления всей стратегии.

**Состояния исполнения (проверять свежий журнал, не угадывать):**
- `SLEEPING`: CHAT может продолжать свою независимую разработку с lock.
- `AWAKE + WORK_EXECUTION=NOT_STARTED`: Work доступен, но ещё **не запущен**. CHAT прекращает независимую разработку, подготавливает **один короткий переход** для 👤 ДИМЫ без лишней переписки; не утверждать передачу как выполненную.
- `WORK_EXECUTION=STARTED/RUNNING`: только если работа реально началась и это подтверждено. Дальнейшее распределение задач ведёт SOL.
- `AWAKE + WORK_EXECUTION=COMPLETED`: прежний Work-сеанс завершён; проверить NEXT_AGENT, прямое назначение, live GitHub lock. Новый CHAT-блок разрешён только по действующему поручению пользователя или делегированию SOL, без конкурирующей записи.

**Формат передачи в другой чат (приоритет §4.10):** получатель при следующем реальном ходе **сам** открывает актуальные AGENTS.md, журнал, план и протоколы из GitHub. Ручная передача всего контекста, включая копию стандарта, **не нужна**, если GitHub доступен адресату. При необходимости нового запуска другого чата пользователь даёт короткую команду перечитать канон; кнопку копирования короткой команды показывать только если она реально уменьшает действия. Полный GenUI.copy(fullHandoff) применять только при недоступности GitHub или прямом запросе полного экспорта. GenUI.issueNewTurn запускает новый ход лишь в этом же чате; не заявлять межчатовую доставку или фоновое исполнение.

**Требование к первому ответу SOL:** подтвердить восстановление ответственности за **весь** проект, проверить все источники и реальную сборку, независимо пересмотреть приоритеты и уже сделанное, затем самостоятельно продолжать работу. Промпт не должен ограничивать SOL одной интеграцией/приёмкой без проверки стратегии. Не создавать новую параллельную управляющую систему; обновлять существующие документы.
