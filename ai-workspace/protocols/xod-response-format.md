# XOD — канонический формат ответов

**Версия 2.0 · 21.11.2026 · утверждена 👤 ДИМОЙ.**  
**Цель:** минимизировать время чтения, когнитивную нагрузку и число действий пользователя. **Чат — изменения и решения; GitHub — полные результаты и рабочая память.**  
**Источник истины:** этот файл в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Новые прямые инструкции 👤 ДИМЫ имеют приоритет. Не создавать копии шаблона с другими названиями.

## 1. Показывать только новое

**Основной принцип — «дельта вместо полного отчёта».** Каждый содержательный ответ показывает, что изменилось **со времени предыдущего ответа**, а не пересказывает весь проект и прежние итерации.

Порядок важности:
1. **Результат:** одна человеческая фраза о полезном изменении.
2. **Доказательство:** один показатель фактически выполненных проверок, если они были, либо точный статус «не проверено».
3. **Результат в GitHub:** одна-две ссылки на конкретный пакет и живой журнал, если запись выполнена.
4. **Ориентация:** текущий шаг, следующий шаг, нужное действие 👤 ДИМЫ.
5. **Подробности:** в GitHub или раскрываемом блоке, а не в основном потоке чтения.

Не повторять прежние показатели, лимиты, длинные технические детали, неизменившиеся статусы или сам план без необходимости. **Исключения:** всегда кратко показывать текущий шаг и действие 👤 ДИМЫ. Существенный риск, требующий решения пользователя, **не прятать** в раскрываемые подробности.

## 2. Навигация и роли

Всегда сохранять каскад **от стратегии к тактике**, минимум четыре уровня; номера этапов не переизобретать между ответами:

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.5. Сохранение`

- **Текущий шаг** указывать явно с номером и исполнителем в одном фиксированном месте отчёта: `1.1.1.5 · 🟦 CHAT`.
- **Следующий шаг** показывать отдельно, только когда он действительно отличается; назначать ему реального исполнителя. Не придумывать следующий номер при продолжении того же шага.
- Хронологические события внутри шага: `1.1.1.5.1`, `1.1.1.5.2`, `1.1.1.5.3`. Они обозначают события, **не** новые уровни стратегического плана.
- 🟦 **CHAT** — подготовка, тесты, патчи; 🟩 **SOL** — Work-интеграция локальной сборки; 🟪 **ASTRA** — архитектурная эскалация; 👤 **ДИМА** — пользователь.
- Не предполагать, что SOL проснулся, получил сообщение или увидел GitHub. До прямого сообщения 👤 ДИМЫ состояние SOL — `SLEEPING`. Лимиты приводить как *последние сообщённые*, не как текущий остаток.

## 3. Промежуточные сообщения

У промежуточных сообщений должен быть явно **другой визуальный язык**, чем у финала: **одна Markdown-цитата** с узнаваемым маркером, без общей финальной рамки:

> **◌ ПРОМЕЖУТОЧНО · 🟦 CHAT · 1.1.1.5**
>
> Подтверждена причина […]. Сейчас выполняю проверку […].

Отправлять только при появлении полезного факта, реального препятствия или существенной операции; не писать пустые обновления для видимости активности. Промежуточное сообщение — не финальный результат, не означает работу в фоне между ходами и не заменяет запись в GitHub.

## 4. Финальный шаблон 2.0

Для содержательного результата **весь финальный ответ помещать в одну нейтральную внешнюю рамку** (в ChatGPT, поддерживающем богатую разметку: `<box border radius="xl" padding={3} gap={3}>` и `</box>`). В клиенте без рамок — компактный Markdown-эквивалент. Без дополнительных цветных итоговых карточек и повторных заголовков.

**А. Начало, три короткие строки максимум:**
- `XOD · CHAT 08` и **не более одного** статуса вроде `Готово`, только если это правда.
- Компактный четырёхуровневый путь из §2.
- **`Результат: …`** — одна фраза понятным языком.

**Б. Хронология, обычно две-три отдельные цитаты; четвёртая — только при необходимости:**
- `1.1.1.5.1 · Найдена проблема` — если проблема воспроизведена; иначе `Подготовлено`.
- `1.1.1.5.2 · Разработано и проверено` — изменение и **один** агрегированный результат вроде `14/14 PASS`. Не дублировать тесты в нескольких местах.
- `1.1.1.5.3 · Записано для SOL` — пакет и журнал, только если реально записаны. «Записано для SOL» **не означает, что SOL уже прочитал**.
Не создавать фиктивные события ради соблюдения числа цитат. Историю и технические подробности размещать в GitHub.

**В. Нижняя зона, всегда на одном месте:**
- `Текущий шаг → [номер] · [исполнитель]`; далее `Следующий → [номер] · [исполнитель]`, если другой.
- `👤 ДИМА: действий не требуется` либо **одно конкретное действие** с минимальными усилиями.
- Состояние SOL упоминать дополнительно только при изменении или если от него зависит следующее действие.

**Г. Подробности, необязательные:** для технических оговорок, разбиения тестов и второстепенных ограничений использовать раскрываемый `popover` с названием «Ограничения и технические подробности», а при его отсутствии — ссылку на GitHub. **Критическую угрозу данным, существенную неуверенность или необходимость согласования всегда показывать открыто.**

**Д. Если это рабочий чат разработки XOD:** добавлять действующую кнопку продолжения по §7 только при выполнении условий; её не надо вставлять в ветку оформления шаблонов.

Для коротких вопросов и простых ответов не принуждать пользователя читать рамку с искусственными этапами. Не добавлять таблицы, изображения, многочисленные бейджи или диаграммы ради оформления, если они не уменьшают время понимания.

## 5. Компактный образец (условный)

```text
┌ XOD · CHAT 08                                     Готово
│ 1 → 1.1 YouTube → 1.1.1 Виды таблицы → 1.1.1.5 Сохранение
│ Результат: настройки нескольких таблиц больше не перезаписывают друг друга.
│
│ > 1.1.1.5.1 · Найдена проблема
│ > Два сохранения могли перезаписать друг друга.
│
│ > 1.1.1.5.2 · Разработано и проверено
│ > Добавлен координатор. 14/14 тестов PASS.
│
│ > 1.1.1.5.3 · Записано для SOL
│ > [Пакет CHAT 08] · [Канонический журнал]
│
│ Текущий шаг → 1.1.1.5 · 🟦 CHAT
│ Следующий → 1.1.1.6 · 🟦 CHAT
│ 👤 ДИМА: действий не требуется.
│ [Раскрыть технические подробности]
└─────────────────────────────────────────────────
```

Это пример последовательности, **не новая фактическая сводка XOD**. В реальном ответе использовать одну рамку и **настоящие отдельные Markdown-цитаты**, а не рисовать ASCII-контур.

## 6. Точность статусов и проверок

- **Подготовлено:** код/патч написан, без утверждения, что он протестирован.
- **Проверено:** фактически выполнены тесты; указать среду и результат, обычно одной агрегированной цифрой.
- **Опубликовано:** записано в GitHub; «проверено после публикации» — только если файл перечитан.
- **Интегрировано:** действительно работает в локальной XOD, после её регрессионной проверки, а не только в автономном стенде Chromium или имитации storage.
- **Передано SOL:** создан доступный для будущего чтения журнал/пакет; не равно «SOL увидел» или «SOL принял».
- **Утверждено 👤 ДИМОЙ:** только по его явному решению.
- **Текущие лимиты, модель, пробуждение, фон:** ничего не приписывать без данных.
- Не выдумывать пути и не называть непроверенные проверки выполненными.

## 7. Одно нажатие «Продолжить XOD · GPT-6 High»

Это **ранее принятое правило**, сохранено. Полный протокол рабочего цикла — `ai-workspace/protocols/xod-autonomous-worker.md`, §2.

В **рабочем чате разработки XOD**, когда остались доступные автономные задачи и не требуется решение 👤 ДИМЫ, после финального отчёта размещать **одну действующую кнопку** «Продолжить XOD · GPT-6 High», если доступен прямой host action `GenUI.issueNewTurn`. По нажатию он отправляет короткую команду продолжения **в этот же чат** после чтения GitHub checkpoint. Не использовать кнопку в ветке редактирования данного формата и в ветке автоматизаций.

Кнопка не переключает модель и не подтверждает, что выбран High; 👤 ДИМА выбирает режим в меню ChatGPT. Одно нажатие — **один новый ход**, не бессрочное выполнение в фоне. Не показывать недействующие или декоративные кнопки.

## 8. Общая рабочая память и границы

- Канонический журнал: `ai-workspace/handoffs/work-resume-latest.md`; обновлять после каждого существенного технического результата, фиксируя результат, проверку, риск и следующий шаг.
- Пакеты кода, патчей и тестов: `ai-workspace/submissions/chat-NN/`. Одна актуальная версия на артефакт, не создавать копии журналов.
- Ветка `main` не меняется без прямого поручения. Не терять локальные правки SOL и не утверждать их интеграцию без тестирования.
- Корневой `AGENTS.md` уже указывает на этот канонический файл. **GitHub не обеспечивает автоматическое распространение инструкции на все чаты ChatGPT:** агент должен получить проектный контекст или прочитать ссылку. Не обещать глобального применения без настройки.
- Если запрос посвящён **шаблону ответов**, не уходить в разработку XOD и не добавлять кнопку разработки.
- Новые утверждённые изменения форматирования править **в этом же файле**, не создавать `final-v2` или параллельные каноны.

## 9. Самопроверка перед финальным ответом

1. Пользователь сразу видит **результат**, а не длинный процесс?
2. Есть четыре уровня навигации, явный **текущий шаг** и правильная роль?
3. В цитатах только **новые реальные события**, хронологически, без повтора прежнего?
4. Показатели проверок точны; «опубликовано», «проверено», «интегрировано» не смешаны?
5. Риски, требующие решения 👤 ДИМЫ, остались **видимыми**?
6. Ссылки ведут к конкретным актуальным артефактам, и заявление об их проверке подтверждено?
7. Текущий/следующий шаг и действие 👤 ДИМЫ находятся внизу, без дублирования?
8. Промежуточные сообщения **цитаты с маркером**, финал содержательной работы — **одна рамка с хронологическими цитатами**?
9. Кнопка продолжения реально работает и находится только в рабочем чате XOD?
10. Не утверждаются автоматическая синхронизация между чатами, запуск в фоне, пробуждение SOL или настройка модели без проверки?

**Правило обновления:** последнее прямое указание 👤 ДИМЫ приоритетнее этого файла. Утверждённое изменение вносится в этот же канонический файл с проверкой внутренней согласованности и связанных указателей.
