# XOD — канонический формат ответов

**Версия 2.3 · 21.11.2026 · строгая спецификация по запросу 👤 ДИМЫ.**  
**Цель:** минимизировать время чтения, когнитивную нагрузку и число действий пользователя. **Чат — изменения и решения; GitHub — полные результаты и рабочая память.**  
**Источник истины:** этот файл в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Новые прямые инструкции 👤 ДИМЫ имеют приоритет. Не создавать копии шаблона с другими названиями.

## 1. Показывать только новое

**Основной принцип — «дельта вместо полного отчёта».** Каждый содержательный ответ показывает, что изменилось **со времени предыдущего ответа**, а не пересказывает весь проект и прежние итерации. **Контекстная шапка обязательна в каждом ответе**: её краткое повторение нужно для ориентации и не считается запрещённым дублированием.

Порядок важности:
1. **Результат:** одна человеческая фраза о полезном изменении.
2. **Доказательство:** один показатель фактически выполненных проверок, если они были, либо точный статус «не проверено».
3. **Результат в GitHub:** одна-две ссылки на конкретный пакет и живой журнал, если запись выполнена.
4. **Ориентация:** текущий шаг, следующий шаг, нужное действие 👤 ДИМЫ.
5. **Подробности:** в GitHub или раскрываемом блоке, а не в основном потоке чтения.

Не повторять прежние показатели, лимиты, длинные технические детали, неизменившиеся статусы или сам план без необходимости. **Исключения:** всегда показывать контекстную шапку; для работы — кратко указывать текущий шаг и действие 👤 ДИМЫ. Существенный риск, требующий решения пользователя, **не прятать** в раскрываемые подробности.

## 2. Навигация и роли

Для содержательных задач XOD сохранять каскад **от стратегии к тактике**, минимум четыре уровня; номера этапов не переизобретать между ответами. **Путь принадлежности контекста** (§2.1) и **номер шага** — разные навигационные оси: не добавлять вымышленные уровни принадлежности ради четырёх уровней рабочего плана:

`1. XOD 3.0 → 1.1. YouTube → 1.1.1. Виды таблицы → 1.1.1.5. Сохранение`

- **Текущий шаг** указывать явно с номером и исполнителем в одном фиксированном месте отчёта: `1.1.1.5 · 🟦 CHAT`.
- **Следующий шаг** показывать отдельно, только когда он действительно отличается; назначать ему реального исполнителя. Не придумывать следующий номер при продолжении того же шага.
- Хронологические события внутри шага: `1.1.1.5.1`, `1.1.1.5.2`, `1.1.1.5.3`. Они обозначают события, **не** новые уровни стратегического плана.
- 🟦 **CHAT** — подготовка, тесты, патчи в период сна SOL либо по его подтверждённому делегированию; 🟩 **SOL** — главный оркестратор всей разработки XOD, включая стратегию, распределение работ, интеграцию и контроль; 🟪 **ASTRA** — архитектурная эскалация; 👤 **ДИМА** — пользователь.
- Не предполагать, что SOL проснулся, получил сообщение или увидел GitHub. До прямого сообщения 👤 ДИМЫ состояние SOL — `SLEEPING`. Лимиты приводить как *последние сообщённые*, не как текущий остаток.

### 2.1. Обязательная контекстная шапка — строгий стандарт 2.3

**Первой содержательной областью каждого ответа** должна быть контекстная шапка. Её три независимых поля:

- **ТИП КОНТЕКСТА** — что за объект обсуждается: `ПРОЕКТ`, `ПРОЦЕСС`, `ЗАДАЧА`, `ДОКУМЕНТ`, `ВОПРОС`, `ИССЛЕДОВАНИЕ`, `ТЕМА` или другой точный тип. Не называть всё подряд «темой». Выбирать один ведущий тип для текущего ответа, даже если объект связан с несколькими.
- **ЗАГОЛОВОК** — короткое **КОНКРЕТНОЕ НАЗВАНИЕ ТЕКУЩЕГО КОНТЕКСТА ЦЕЛИКОМ КАПСОМ**. Это главный визуальный ориентир. Не превращать весь текст ответа или все заголовки в капс. Не писать только `XOD · CHAT 08` вместо смысла ответа: идентификатор пакета, роль и статус — вторичные метаданные.
- **ПУТЬ ПРИНАДЛЕЖНОСТИ** — компактная иерархия реально известных родительских объектов, например `LIFE OS → XOD → Управление ИИ → Шаблон ответов`. Она показывает, где находится объект, но не является номером рабочего этапа; глубина определяется реальной структурой, а не фиксируется искусственно. При неясной принадлежности показать ближайший достоверный уровень и не выдумывать недостающие.

**Нормативный вид (без альтернативного порядка при поддержке компонентов):**

```text
ДОКУМЕНТ · ТЕКУЩИЙ КОНТЕКСТ
НАВИГАЦИЯ ПО КОНТЕКСТАМ ЧАТА
LIFE OS → XOD → Управление ИИ → Шаблон ответов
[КОНТЕКСТЫ ЧАТА · 3 ▾]  ← только кнопка раскрытия
```

В длинных ответах помещать шапку **внутрь одной внешней рамки** (§4), в коротких — показывать компактным текстом без обязательной рамки. В промежуточных сообщениях добавлять тип и заголовок к маркеру, но не разворачивать карту.

### 2.2. Карта контекстов — доступна всегда, содержимое только при раскрытии

**Последнее решение 👤 ДИМЫ:** в шапке постоянно видна только компактная точка доступа `КОНТЕКСТЫ ЧАТА · N ▾`; **список и описания контекстов скрыты до нажатия**. Это отменяет более ранний вариант «постоянно видимая карта». По умолчанию карта **закрыта**, не открывать её автоматически при смене контекста. Наведение без клика не должно самостоятельно раскрывать список. Если интерфейс поддерживает `popover`, использовать кликабельный `popover-trigger`; иначе нативное раскрытие (если поддерживается) или компактный текстовый аналог без ложных обещаний интерактивности.

Разделять:
1. **ЧАТ** — контейнер разговора; его название не ограничивает будущие контексты.
2. **КОНТЕКСТ** — устойчивый объект обсуждения с одним типом, названием и принадлежностью, например проект, документ или процесс.
3. **КАРТА ЧАТА** — оглавление всех **достоверно обнаруженных значимых контекстов** данного разговора, включая текущий; не список каждого сообщения и не копия внешней карты проекта.
4. **ШАГ** — позиция в выполнении работы внутри выбранного контекста; не равен теме ответа и не меняется только из-за смены темы.

**Правила ведения карты:**
- В раскрытом виде помечать текущий контекст `СЕЙЧАС` и, при наличии данных, `ОТЛОЖЕНО`, `ЗАВЕРШЕНО`, `В ДРУГОЙ ВЕТКЕ`. Не путать статус обсуждения со стадией реализации кода.
- Сначала пытаться отнести новый вопрос к уже существующему контексту; новый пункт создавать лишь для самостоятельного направления с возможностью продолжения. Не создавать «темы» для каждого уточнения.
- Если контекстов много, показывать компактные названия и группы (при необходимости 3–5 основных плюс раскрываемый остаток внутри карты). Не повторять в карте длинные описания и результаты прошлых шагов.
- При переключении темы менять **текущую шапку**, но не удалять предыдущие контексты из карты. Перенос в другую ветку отмечать **только по подтверждению**; не считать перенос завершением проекта.
- **Не выдумывать полный индекс**, когда часть истории недоступна: отражать только известные контексты и указывать ограничение охвата. `N` приводить только при достоверном подсчёте; иначе надпись без числа.
- Карта — **ориентир**, а не автоматическая система навигации к старым сообщениям: не изображать названия ссылками для перехода без реально доступных URL/действий.
- Не создавать новый файл-карту чата или параллельные канонические документы без прямого запроса; краткий индекс можно поддерживать непосредственно в контексте чата.

## 3. Промежуточные сообщения

У промежуточных сообщений должен быть явно **другой визуальный язык**, чем у финала: **ровно одна Markdown-цитата** с узнаваемым маркером, без общей финальной рамки. Состав строки фиксирован §4.3:

> **◌ ПРОМЕЖУТОЧНО · 🟦 CHAT · ДОКУМЕНТ: ШАБЛОН ОТВЕТОВ · 1.1.1.5**
>
> Подтверждена причина […]. Сейчас выполняю проверку […].

Отправлять только при появлении полезного факта, реального препятствия или существенной операции; не писать пустые обновления для видимости активности. Промежуточное сообщение — не финальный результат, не означает работу в фоне между ходами и не заменяет запись в GitHub.

## 4. Строгий макет ответов · версия 2.3

**Нормативный контракт, не свободные рекомендации.** Агенты используют одинаковые порядок, подписи, размеры, рамку и раскрытия. Меняется фактическое содержимое, но не макет. Режимы: **РАБОЧИЙ** (существенный результат, несколько операций/проверок/артефактов), **КРАТКИЙ** (простой ответ) и **ПРОМЕЖУТОЧНЫЙ** (§3, §4.3).

### 4.1. РАБОЧИЙ ответ: фиксированный порядок

1. **ШАПКА** — тип контекста, затем **конкретный смысловой заголовок ЦЕЛИКОМ КАПСОМ**, затем путь принадлежности. Идентификатор CHAT NN и роль вторичны, не заменяют заголовок.
2. **КАРТА ЧАТА** — один всегда видимый триггер `КОНТЕКСТЫ ЧАТА · N` (число только при достоверном подсчёте); при клике раскрывается поповер с достоверными контекстами и маркером `СЕЙЧАС`. **По умолчанию закрыта, от наведения не открывается.** Не показывать вторую карту в основном тексте.
3. **РАЗДЕЛИТЕЛЬ** — ровно один `<divider color="subtle"/>` между шапкой и результатом.
4. **РЕЗУЛЬТАТ** — ровно одна строка `**Результат:** [одна фраза]`, перед остальным содержимым. Не повторять вывод в цитатах и подвале.
5. **СОБЫТИЯ** — от нуля до трёх отдельных Markdown-цитат `<blockquote>` с хронологическими **новыми** фактами. Метка каждой: `**[ID шага] · Найдена проблема/Выполнено/Проверено/Опубликовано/Нужна проверка**`. Не придумывать события ради числа блоков. Указывать один агрегированный результат реально проведённых проверок, а не всё множество старых PASS.
6. **ССЫЛКИ** — до двух обычных ссылок, основной результат и/или живой журнал, только подтверждённые фактические адреса; не делать из них рекламные карточки или кнопки.
7. **РИСК** — одна открытая фраза, только если есть существенный риск, неопределённость или блокер. Риски, меняющие действия пользователя, **не скрывать** в popover.
8. **РАЗДЕЛИТЕЛЬ** — ровно один `<divider color="subtle"/>` перед подвалом.
9. **ПОДВАЛ** — фиксированные строки по порядку: `**Текущий шаг:** [ID и роль]`; `**Следующий шаг:** [ID и роль]` только если он действительно отличается; `**👤 ДИМА:** действий не требуется / одно конкретное действие`. Статус SOL — только при изменении или влиянии на действие.
10. **ДЕТАЛИ** — по необходимости один заключительный popover `ТЕХНИЧЕСКИЕ ПОДРОБНОСТИ` (только по клику) или ссылка на GitHub. Никогда не помещать в него обязательные для решения факты.

**Фиксированные настройки внешнего вида (при поддержке DIL):** одна и только одна рамка `<box border radius="xl" padding={3} gap={3}>`, нейтральный фон. Шапка `<box gap={1}>`. Тип `<text size="2xs" color="secondary" weight="medium">`. Заголовок `<title size="lg">` **капсом**. Путь `<text size="xs" color="secondary">`. Триггер карты `<text size="xs" underline>` с иконками `list-tree` и `chevron-down` при доступности. Для раскрытия `<popover showOnHover={false}>`. Разделители только `<divider color="subtle"/>`. Основной текст стандартного размера. Не менять визуальную иерархию по вкусу агента, не добавлять цветные плашки, лишние заголовки, таблицы, карусели и блоки-обёртки.

**Стандартные подписи (печатать дословно):** `ТЕКУЩИЙ КОНТЕКСТ`, `КОНТЕКСТЫ ЧАТА`, `Результат:`, `Текущий шаг:`, `Следующий шаг:`, `👤 ДИМА:`, `ТЕХНИЧЕСКИЕ ПОДРОБНОСТИ`. Не использовать варианты «ТЕМА ОТВЕТА», «ИТОГ», «КАРТА ТЕМ», «ДАЛЬШЕ», «РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ».

**Нормы краткости:** шапка — 3 короткие строки; результат — одна фраза; каждая цитата — обычно не больше двух коротких смысловых предложений; ссылки — максимум две; подвал — 2–3 строки. Расширять лишь для необходимой точности, безопасности или по запросу.

### 4.2. КРАТКИЙ ответ

Сохранять **тот же тип/заголовок КАПСОМ/путь и один триггер карты**, затем одно-два предложения ответа. Нет искусственных цитат, хронологии, номера шага или подвала без рабочего процесса. На узком экране или для однофразового ответа общая рамка необязательна, но порядок и подписи не меняются.

### 4.3. ПРОМЕЖУТОЧНЫЙ ответ

Только одна Markdown-цитата, без полной финальной рамки, карты и подвала: `◌ ПРОМЕЖУТОЧНО · [РОЛЬ] · [ТИП: ЗАГОЛОВОК КАПСОМ] · [ШАГ ЕСЛИ ЕСТЬ]`. Финальный ответ снова содержит полную шапку и карту. Не выдавать статус за готовый результат.

### 4.4. Fallback без богатого интерфейса

Тот же порядок в Markdown: `ТИП · ТЕКУЩИЙ КОНТЕКСТ` → `# ЗАГОЛОВОК КАПСОМ` → путь → `КОНТЕКСТЫ ЧАТА` → результат → события (если есть) → ссылки → подвал. Не рисовать неработающий «раскрываемый» элемент. Если реального раскрытия нет, написать короткую текстовую ссылку на карту или перечислить достоверные контексты лишь по запросу.

### 4.5. Границы и исключения

- Риски потери данных и необходимые решения всегда видимы; дизайн не должен скрывать существенное.
- Утверждать `Проверено`, `Опубликовано`, `Интегрировано` только по доказательствам (§6).
- **Продолжение разработки:** при `SOL_STATE=SLEEPING` кнопка только по §7. При `AWAKE` переход SOL только по §10 и без same-chat кнопки.
- Диаграммы/таблицы/изображения вместо стандартных абзацев — лишь по содержательной необходимости и явному запросу.
- GitHub сам по себе не распространяет изменения на чаты, которые не перечитали инструкцию (§8).

## 5. Один нормативный образец (иллюстрация, не состояние проекта)

Теги ниже показывают **дословный каркас для DIL**; текст и фактические URL заменяются, отсутствующие действия и события опускаются. Не вставлять этот код как HTML в приложение XOD.

```jsx
<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <text size="2xs" color="secondary" weight="medium">ДОКУМЕНТ · ТЕКУЩИЙ КОНТЕКСТ</text>
    <title size="lg">СТАНДАРТ ОТВЕТОВ</title>
    <text size="xs" color="secondary">LIFE OS → XOD → Управление ИИ → Шаблон ответов</text>
  </box>
  <popover showOnHover={false}>
    <popover-trigger>
      <row align="center" gap={2}>
        <icon name="list-tree" size="sm" color="secondary"/>
        <text size="xs" underline>КОНТЕКСТЫ ЧАТА · 3</text>
        <icon name="chevron-down" size="xs" color="secondary"/>
      </row>
    </popover-trigger>
    <popover-content align="start">
      <box gap={2}>
        <text size="xs">ПРОЕКТ · Разработка XOD</text>
        <text size="xs">ПРОЦЕСС · Автономная работа ИИ — В ДРУГОЙ ВЕТКЕ</text>
        <text size="xs" weight="medium">ДОКУМЕНТ · Шаблон ответов — СЕЙЧАС</text>
      </box>
    </popover-content>
  </popover>
  <divider color="subtle"/>
  **Результат:** [одно реальное полезное изменение].
  <blockquote>**[ID шага] · Выполнено**

  [Одно новое событие.]</blockquote>
  <blockquote>**[ID шага] · Проверено**

  [Один подтверждённый показатель.]</blockquote>
  <Link url="[реальный URL]">[Название результата]</Link>
  <divider color="subtle"/>
  **Текущий шаг:** [ID и роль].

  **Следующий шаг:** [если иной].

  **👤 ДИМА:** [действие или действий не требуется].
</box>
```

Результат, проверки, URL и идентификаторы в примере — **плейсхолдеры**, не новые факты XOD. Цитаты и строки с отсутствующими данными **не выводятся**; нельзя оставлять фиктивные значения. В fallback без DIL использовать те же подписи, не ASCII-рамку.
## 6. Точность статусов и проверок

- **Подготовлено:** код/патч написан, без утверждения, что он протестирован.
- **Проверено:** фактически выполнены тесты; указать среду и результат, обычно одной агрегированной цифрой.
- **Опубликовано:** записано в GitHub; «проверено после публикации» — только если файл перечитан.
- **Интегрировано:** действительно работает в локальной XOD, после её регрессионной проверки, а не только в автономном стенде Chromium или имитации storage.
- **Передано SOL:** создан доступный для будущего чтения журнал/пакет; не равно «SOL увидел» или «SOL принял».
- **Утверждено 👤 ДИМОЙ:** только по его явному решению.

## 10. Пробуждение Work: SOL возвращается как руководитель, не как исполнитель интеграционного поручения

**Норматив:** `AGENTS.md`, `ai-workspace/protocols/xod-autonomous-worker.md` §4 и `ai-workspace/handoffs/work-resume-latest.md` §24. При сообщении 👤 ДИМЫ, что Work доступен, нельзя автоматически делать очередное задание SOL «интегрировать CHAT 04–12», даже если это заметная техническая задолженность. Эта работа — только возможная подзадача, выбираемая SOL после восстановления всей стратегии.

**Три разных состояния:**
- `SLEEPING`: CHAT может продолжать свою независимую разработку с lock.
- `AWAKE + WORK_EXECUTION=NOT_STARTED`: Work доступен, но ещё **не запущен**. CHAT прекращает независимую разработку, подготавливает **один короткий переход** для 👤 ДИМЫ без лишней переписки; не утверждать передачу как выполненную.
- `WORK_EXECUTION=STARTED/RUNNING`: только если работа реально началась и это подтверждено. Дальнейшее распределение задач ведёт SOL.

**Формат передачи в другой чат:** кнопка «Скопировать восстановление SOL» вызывает `GenUI.copy(fullHandoff)` и включает **внутри копируемого текста** ссылку на весь журнал и §24, исходную стратегию XOD 3.0 → 3.0b → 3.3, запрос аудита всех накопленных CHAT-пакетов и реальной сборки, проверки тестов/альтернативных патчей, сохранение истории SOL, полноценные полномочия руководителя, обязанность продолжить наиболее полезную работу и правила безопасности. 👤 ДИМА открывает **старый Work-чат SOL** и вставляет текст. `GenUI.issueNewTurn` отправляет в этот же чат и не может перенести поручение в другой; `GenUI.copy` не открывает чат, не меняет модель и не отправляет сообщение.

**Требование к первому ответу SOL:** подтвердить восстановление ответственности за **весь** проект, проверить все источники и реальную сборку, независимо пересмотреть приоритеты и уже сделанное, затем самостоятельно продолжать работу. Промпт не должен ограничивать SOL одной интеграцией/приёмкой без проверки стратегии. Не создавать новую параллельную управляющую систему; обновлять существующие документы.
