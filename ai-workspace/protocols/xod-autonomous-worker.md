# XOD · протокол исполнения: один ответственный исполнитель; Work в резерве

**Версия 2.2 · 2026-11-23 · прямое утверждение пользователя.** Новая модель заменяет обязательное разбиение на отдельные планирующий и исполнительный чаты; её цель — проверенный продуктовый результат с минимумом ручных действий и премиальных расходов. Раньше обязательная последовательность CHAT-PLAN → CHAT-EXEC → SOL вынуждала пользователя многократно вручную запускать и связывать сессии. Это отклонение от целевой автономности. Наличие ролей, журналов и чекпоинтов не является продуктовым результатом.

## 0. Действующий цикл: один владелец результата (приоритет над разделами 1–4)

1. **Назначение.** Прямое поручение пользователя делает текущего доступного агента владельцем результата в пределах его реальных инструментов. По умолчанию он сам анализирует, выполняет, проверяет, исправляет, документирует и выдаёт либо **готовую проверенную версию**, либо воспроизводимый blocker. Не предлагать отдельный CHAT-EXEC или SOL, пока действующий агент может закончить доступную часть сам. Стратегический авторитет SOL исторически сохраняется, но Sol как модель **недоступен** при заявленной исчерпанной недельной квоте; нет ожидания или фиктивной межчатовой передачи.
2. **Единая рабочая итерация.** Определи минимальный вертикальный срез с измеримой ценностью и критериями, проверь актуальный GitHub/код/зависимости, захвати законную CAS lease, исполни максимум в текущем ходе, запусти детерминированные QA, сам исправь замеченные ошибки, запиши только существенную дельту и readback, освободи lease. Статусы `PUBLISHED`, `STARTED`, `VERIFIED`, `INTEGRATED`, `ACCEPTED` доказывай отдельно; исходниковый PASS не превращай в release PASS. Если пользовательское утверждение реально необходимо — короткий выбор один раз; в остальных случаях действуй.
3. **Длительность CHAT — не подтверждена фиксированным пределом.** Пользователь наблюдал ≈6 минут, позднее ≈8 минут; это гипотеза о возможных timeouts, а не измеренный универсальный cap. Никакого принудительного 5+1 minute limit или 4–7 запусков как плана до релиза. Работай максимально полно до фактической остановки/ограничения, контролируй real elapsed time и сохраняй проверяемый checkpoint; отдельно считай человеческие действия, model/tool runtime, autonomously running scripts и календарное ожидание. Инженерные часы/6 минут не являются числом сессий. Для длинного теста использовать независимый script/CI, а не ожидание премиальной модели.
4. **Управление стоимостью.** По последнему пользовательскому сообщению недельный премиальный остаток равен 0%, не измерен из ChatGPT UI. Без premium Work, Sol, Astra, платного API/перерасхода. При неизвестном остатке — сначала доступное подтверждение. >10%: только точечно с верхней границей; 5–10%: премиум-старт лишь после нового прямого разрешения; <=5%: остановить некритичное; 0%: не запускать. Любая платная операция требует `scope / why cheap unavailable / budget ceiling / stop loss / release reserve / model / snapshots before-after`. Протокол не может физически ограничить лимиты платформы: честно показывать эту границу. Статистика без snapshots — UNKNOWN.
5. **Передача между агентами — только при положительном выигрыше.** Сначала исследуй собственные инструменты: при наличии локального checkout, GitHub и CLI делай работу сам. Отдельный агент оправдан только отсутствующим критическим доступом, доказанным рисковым конфликтом или независимым специализированным тестом, ценность которого превышает цену передачи. Пользователь не обязан пересылать промежуточные документы/JSON, пока у текущего агента есть иной путь. Новые отдельные чаты пользователь запускает только когда это действительно необходимо; никакой иллюзии отправки соседнему агенту.
6. **Управление незавершёнными решениями без напоминаний.** В конце содержательных ответов по текущему проекту и при смене темы коротко показывай важные `PENDING_APPROVAL / APPROVED_NOT_PUBLISHED / PUBLISHED_NOT_EXECUTED / BLOCKED` с владельцем и следующей проверкой. Не прячь ожидание решения в длинном документе, прямо предупреди, если уходишь к другому вопросу. Уже принятое решение не спрашивай снова. Не создавать календарные/периодические напоминания из этого принципа.
7. **Выполнение и безопасность.** Перед записью всегда свежие `AGENTS.md`, журнал, lease и relevant protocols. Живую чужую lease не перехватывать. Просроченную lease — только CAS и при наличии самостоятельного разрешения/доказательства отсутствия работы; документируй reclaim. Не меняй `main` без разрешения, не публикуй приватные данные или точный полный source. Нельзя объявить завершённой локальную интеграцию, если у агента нет доступа к ней. Пользователь явно сообщил, что SOL больше недоступен, а окончание доступности не означает завершение 3.0.
8. **Сценарный бюджет, НЕ замер:** остаток 3.0 = 9–23 активных инженерных часов плюс 5–10 ч резерва; вся оставшаяся цепь 3.0–3.6 = 218–459 ч плюс резерв 5–10 = 223–469 ч. Доказанных данных для числа CHAT-сессий до релиза НЕТ; прежний 4–7-цикл признан необоснованным предсказанием. Новая локальная автоматизация сборки **не является** эмпирическим сокращением часов написания кода и не оправдывает произвольное уменьшение этих диапазонов. Показатели выдавать раздельно: latency ответа, execution minutes, часы инженерной работы, wall time автономных тестов, user actions, Work %. Полная карта 8 этапов / 37 подшагов и её 5 метрик сохранены в response-format §§4.6–4.8, 4.13.

**Переход управления по сообщению пользователя 22.11.2026:** SOL quota exhausted, текущая деятельность SOL прервана, доступный CHAT теперь выполняет утверждённую реорганизацию стандартов; код и фактическая release acceptance остаются такими, как указано в последнем проверенном journal §71. Планирующая/исполнительная специализации — необязательные роли внутри единого исполнения, а не требование ещё одного чата.

**Проверяемые полные пользовательские рабочие циклы в `HOLST 2` (время между запросом и последним ответом до нового запроса, не токены и не чистое CPU-время):**

Это не «другой моделью за 6 минут сделана двухчасовая работа». Не подменять эту архитектуру 4–7 вручную запускаемыми шестиминутными CHAT-сессиями и не обещать `4–7` до релиза; этот старый ориентир сохраняется только как неподтверждённый ближайший организационный цикл, не как цель эффективности.

**Практический действующий контракт:** для полноценного Claude-подобного цикла нужен *фактически доступный* долгоживущий исполняющий контур с исходным checkout, правом исполнения скриптов, хранением файлов/кода и возможностью довести до проверенного артефакта. При его отсутствии стандартный чат может выполнять только реально доступный вертикальный срез; не обещать фоновое исполнение и не перекладывать на пользователя 100+ запусков. Стараться при доступной среде паковать тесты, сборку, исправления и релиз в **одну завершаемую задачу**, а не в десятки межчатовых сообщений. **Качество:** отдельно отмечать тестируемые локальные/синтетические проверки и непроверенные browser/cloud gates; скоростные архивные релизы не заменяют приёмку.

### 0.2. Реально проверенный офлайн-цикл сборки и тестов: `xod-cycle.py` (22.11.2026)

**Новый канонический исполняемый инструмент, без сторонних платных сервисов:** [ai-workspace/tools/xod-cycle.py](../tools/xod-cycle.py). Python 3.10+, а для синтаксической проверки JS нужен установленный Node.js; `--browser-test` требует действительно установленный Playwright Chromium. Запускается только по прямой команде агента/пользователя в реальной среде; **GitHub-публикация Python-файла не создаёт запущенного фонового агента на Windows пользователя.** Не включать autorestart/watchdog, не устанавливать программы пользователю без необходимости. Скрипт читает ZIP/каталог из доверенного источника, создаёт временную изолированную копию, выполняет выбранную recipe, собирает пакет, пишет `cycle.json` + `cycle.log` + SHA256. Не меняет входной ZIP, `main`, реальный Test13, облако, приватную доску и не отправляет данные в сеть; **исходные скрипты проекта могут иметь свои сетевые действия**, поэтому доверие к исходнику — предусловие.

**Режимы:** `legacy224` (`v224/patch224.py` → `holst.html` → проверки `node --check` → ZIP приложения и расширения) и `xod3` (`build.py dist` → пакет `dist/`, при явном `--browser-test` — `tests/app_regression.py`). Не подразумевать одинаковую структуру всех Test13; если recipe не подходит, gate BLOCKED и нужна адаптация по **действительному source**, не ложный успех. Автоматическое определение предпочитает `xod3`, когда есть `build.py`.

**Доказательство из текущего runtime, а не будущий эффект:** по настоящему `holst-devkit-2.24.zip` исходного пользователя изолированный `legacy224` build + inline Node.js syntax **PASS**, app ZIP + extension ZIP + standalone HTML получены, ZIP-slip negative test **BLOCKED как положено**, рабочий отчёт показывает `product_release_accepted=false`, Drive `NOT_RUN`. Обычный цикл после локальных файлов ~2.0–2.5 сек в данной среде; не объявлять это временем разработки 3.0. При `--browser-test` smoke корректно вернул `BLOCKED_ENVIRONMENT` из-за отсутствующего Playwright Chromium executable; пакет **сохранён**, но browser PASS не заявлен. Это проверка сборочной автоматизации **старой 2.24**, не XOD 3.0, не Chrome/Edge на компьютере пользователя. Истинная live Test13/Drive/производительность всё ещё требуют текущего host checkout.

**Действующий контракт для внедрения в проект:** сначала пытаться использовать один scriptable цикл, а не требовать от пользователя повторно запускать 4–7 чатов; мерить исход/время/цену по реально выполненным итерациям, не по токенным фантазиям. При отсутствии доступа к реальному Test13 не форсировать подмену source файлом 2.24; это ограничение доступа, а не повод для премиального SOL. Пример только для доверенного архивного devkit:
```bash
python ai-workspace/tools/xod-cycle.py --source holst-devkit-2.24.zip --out ./xod-cycle-out
```
Чтобы проверить браузер **после установки поддерживаемого browser executable**, добавить `--browser-test`; при отсутствии браузера не получать PASS. `--out` должен быть новым/пустым, чтобы не потерять старые результаты.

### 0.4. Публикация патча с проверкой точных байтов (22.11.2026)

Фактическая ошибка CHAT43–45: передача `.patch` через временную Library + Files read иногда **отбрасывала заключительный перевод строки**. После этого `git apply` отвечал `corrupt patch`, хотя локально исходный патч применялся. Это не дефект продукта, но блокирует применение уже проверенного исправления. Все три опубликованных патча исправлены до исходных байтов 22.11.2026.

**Обязательный минимальный приёмочный gate для source-only патчей:** после записи в GitHub прочитать файл заново и сверить `blob SHA` с Git blob SHA исходного локально проверенного файла (включая терминальный `\\n`), а также `git apply --check` для точно этих байтов на изолированной копии подтверждённого исходного модуля. `content readback` после промежуточной текстовой передачи без побайтовой SHA-проверки недостаточен. При выявлении разницы восстановить исходные байты через SHA/CAS `update_file`, не считать устаревший commit принятым. Не загружать приватный source в GitHub, публиковать только узкие патчи и тесты.

## Исторический протокол CHAT-PLAN → CHAT-EXEC (необязателен; при противоречии действует §0)

## Контракты
- Канонический журнал: `ai-workspace/handoffs/work-resume-latest.md`; всегда читать текущие `SOL_STATE` и `WORK_EXECUTION`, а не полагаться на прежнее `SLEEPING`.
- Канонический формат сообщений: `ai-workspace/protocols/xod-response-format.md`.
- Блокировка: `ai-workspace/handoffs/chat-run-lock.json`.
- Рабочий код/тесты: `ai-workspace/submissions/chat-NN` в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Не менять `main`.
- 🟩 SOL — **главный стратегический владелец XOD и интеграционный авторитет**; 🟦 CHAT-PLAN — пользовательский операционный планировщик; 🟦 CHAT-EXEC — отдельно запускаемый пользовательским сообщением исполнитель, при актуальном журнале `WORK_EXECUTION=COMPLETED / NEXT_AGENT=CHAT` и свободной lease. Прямое поручение 👤 ДИМЫ подтверждает ограниченную автономию CHAT-EXEC, не является стартом Work или интеграцией SOL. Предыдущие Scheduled задания не возобновляются автоматически.

## 1. Общие гарантии каждого цикла
1. Прочти актуальный журнал. **Scheduled/автономные фоновые задачи** не начинают разработку, когда SOL_STATE != SLEEPING. **Исключение только для свежего прямого поручения пользователя отдельному CHAT-EXEC** при `SOL_STATE=AWAKE + WORK_EXECUTION=COMPLETED + NEXT_AGENT=CHAT` и документированном task assignment; если `NOT_STARTED`, `STARTED`, `RUNNING` либо назначение отсутствует, исполнитель останавливается. Любую живую lease другого агента не обходить.
2. Прочти lock и его blob SHA. Если `state=running` и срок `expires_at` в будущем — не начинать параллельную работу. Если idle/истекло — захвати через GitHub update_file с текущим `sha` (оптимистическая блокировка). При конфликте SHA остановись. Выбирай уникальный owner на каждый запуск.
3. Lock lease до 70 минут, но после завершения обязательно освободи. Если работа длится дольше 15 минут — обновляй heartbeat и продлевай expires_at по актуальному sha. Перепроверяй блокировку и SOL_STATE перед каждым существенным коммитом. Не изменяй чужие данные и не форсируй SHA.
4. Работай максимально содержательно: тесты, воспроизводимые дефекты, высокоценный автономный патч, модуль, непрерывные проверки, но избегай фантазий об актуальной локальной сборке SOL. Используй оригиналы в GitHub; сохраняй неинтегрированные исправления SOL. У задачи должен быть наблюдаемый результат, а не «видимость деятельности».
5. После каждого существенного результата **обновляй существующий журнал** с выполненным, проверенным, непроверенным, ссылками, рисками и следующим действием. Оставь checkpoint, чтобы следующий запуск не повторял работу. Если остаётся полезная самостоятельная работа — продолжай в текущей итерации, а не останавливайся ради расписания.

```text
    → TASK-A-017: защита от поздней записи [3/5 PASS = 60%, Δ+20 п.п.]
       [██████░░░░] 60% | статус: SOURCE_VERIFIED / E2E_OPEN
       ✓ C1 воспроизведён исходный FAIL — commit/test ref
       ✓ C2 исправлено на текущем source — exact SHA
       ✓ C3 negative/positive Node tests — runner/result
       ○ C4 integrated browser test — NOT_RUN
       ○ C5 rollback/regression — NOT_RUN
  Следующий: C4, владелец A, blocker browser runner
```

Пример полностью **иллюстративный**, не фактические проценты XOD. Каждый критерий имеет постоянный ID, недвусмысленный PASS-признак, вес (по умолчанию равный, иначе заранее зафиксированный), источник доказательства и свой gate-class. **Task progress = сумма весов только проверенных PASS критериев / сумма изначально утверждённых весов.** `Δ` относительно прошлого user trigger из закреплённого checkpoint, не относительно размноженных patch commits. Если плановые критерии неизвестны — `н/д: требуется критерий`; не считать незапланированные задачи как PASS. Для уровня релиза/потока фиксировать acceptance gates (состояния `PASS/FAIL/BLOCKED/NOT_RUN`), а не механически средний процент leaf задач: код/тесты не равны интеграции/релизу. Частичная проверка не приносит полный вес, если не выделена как отдельный заранее заданный критерий. Тест с mock не даёт real E2E credits. При пересмотре scope показать старую/новую базу и причину; нельзя повышать процент от добавления/удаления задач. Если реальный test ранее PASS перестал быть валиден, явное `evidence invalidated` и корректировка вниз.

**В финальном ответе и перед продолжением:** (a) fixed hierarchy root→lane→milestone→active-task→criteria, (b) current bar, previous/now/Δ, (c) реально пройденные и оставшиеся criteria с доказательствами, (d) новые задачи: `NEW/OUT_OF_BASELINE` без прибавки прогресса, (e) `BLOCKED` и альтернативы; (f) следующий владелец и конкретный источник. Если `Δ=0` — написать `СТОИМ НА МЕСТЕ`, перечислить новые subtask и почему они не повысили acceptance progress; если два триггера `Δ=0` подряд — до третьего триггера рассмотреть замену подхода, упрощение/отказ от лишнего, другой runner/доступ, один короткий запрос пользователя. При скрытом/неопределённом gate процент заменяется `н/д`, а не выдуманным 0–99%.

**Представление:** для рабочего хода мини-панель текущей ветки с баром и раскрытым критерием; при запросе пользователя — все уровни текущей задачи. Для каскадной карты всей дорожной сети действующий UX 8 релизов / 37 подшагов и пять метрик сохранён, не смешивать его экспертные оценки часов с данным gate-прогрессом.

### 0.6.3. Cloud-first execution/verification и право на Work

Основная среда XOD = private GitHub `PodkinDmitry/xod-private`, сейчас изолированные продуктовые `pilot/xod3-foundation`, `pilot/youtube-beta` от `release/xod-3.0` baseline `c6cfb259...`. Старый частный Windows Test13 нужен **лишь** если именно Windows/Edge/реальные профили или пользовательская UI-приёмка оказываются специфическими gates. В остальных случаях repo clone + build.py в чистом cloud/sandbox + Playwright/App/Chromium MV3 in separate profiles; хранить только синтетические test data, исключить приватные доски, токены и старую Git-историю, иметь rollback. GitHub Actions для private repos может потреблять квоту; проверять реальный billing/budget и запрещать оплату сверх включённого лимита до включения workflow.

**Web browser внутри ChatGPT** полезен для UI smoke/ручной инспекции страницы в доступном режиме Work/Codex, но не заменяет загружаемое расширение MV3/программатическую проверку IndexedDB/долгий benchmark. Cloud Playwright bundled Chromium поддерживает MV3 extension через persistent context; named Google Chrome/Microsoft Edge могут не поддерживать sideload flags, поэтому separate true-browser compatibility gate останется. Пользователь допускает быть тестировщиком по коротким сценариям *только после* самоисполняемых проверок, с готовой test beta/backup/rollback и максимумом диагностических данных, не как оператор каждой команды.

**Связка CHAT + optional Work/Codex:** CHAT coordinator назначает scope, критерии, бюджет, SHA, рабочую ветку, контрольный останов и приёмку; A/B ordinary chats в Plus исполняют source changes; cheap deterministic CI выполняет build/test и возвращает logs; если есть доступная квота Work/Codex, пользователь может *явно* запустить отдельное узкое cloud coding/browser task, не передавая ему собственность roadmap или право merge/main/release. Work/Codex публикует branch/PR/logs и закрывает поручение; CHAT coordinator самостоятельно проверяет и решает, интегрировать ли. Если quota 0/UNKNOWN — Work не запускать. GitHub journal служит handoff; автоматическая доставка результатов другому живому CHAT без его вызова не заявляется. Полноценный Claude-подобный «непрерывный исполнитель» требует не только CI, но **persisted executable coding agent runtime + agent budget**; GitHub Actions сами не генерируют код.

### 0.6.4. Ошибка прежнего плана и обязательный анти-блокер

**Наблюдаемая ошибка прошлого управления:** множество source-only стендов/патчей были разработаны без доступа к актуальному интегрированному private Test13 source, а безопасное перенесение в приватный GitHub пользователь предложил поздно. Причины: план оценивал локальные узкие задачи и модельные лимиты, но не проверил `source availability` как условие успешной интеграции, не сравнил простую разовую пользовательскую операцию с десятками циклов обхода, и не зафиксировал стоп-сигнал для повторной работы без интегрируемого source. Время пользователя и количество тупиков не были главной измеряемой целью. Это **ошибка организации, не техническая неизбежность**; не выдавать за доказанный конкретный внутренний мотив других агентов.

**Новое правило GATE-0 для любого крупного направления перед задачами:** (1) точный конечный артефакт и критерии, (2) реальный source repo + read/write access + SHA, (3) среды build/test/дистрибуции, (4) стоимость доступа/подключения, включая один безопасный ручной шаг, (5) сравнение трёх архитектурных путей и проверка альтернатив вне буквального prompt, (6) shortest critical path, (7) стоп-признак/escale after 2 attempts without integration progress. Нельзя рапортовать «реализация идёт» при отсутствии source и маршрута интеграции. При риске повторной неинтегрируемой работы остановить кодирование, решить source/billing/browser gate и только потом продолжить.

**Следующий ориентир:** зафиксированный GitHub source/две независимые private ветки решают прежний блокер по исходникам. *Теперь* критический путь — cloud CI/integrated candidate, видимые QA/долгий тест, live Drive только на отдельном тестовом аккаунте, rollback и user acceptance. Сначала повышать доказуемую способность выдавать единый тестируемый artifact, а не количество отдельных «PASS» на mock-стендах.

## 0.7. Координация блокеров A/B: не просить пользователя переносить файлы до устранения инфраструктурной причины (23.11.2026)

**Основание:** прямой запрос 👤 пользователя после того, как A завершил запросом ZIP, а B — сообщением о блокере host-контракта без actionable continuation; оба ответа не содержали рабочей кнопки. Приоритет над прежним `«если нужен source, попроси ZIP»` и менее строгими практиками по автоматическому триггеру.

### 0.7.1. Владелец и классификация

Перед эскалацией установить класс и владельца:

| Класс | Кто владеет | Что делает CHAT A/B | Действие 👤 пользователя |
|---|---|---|---|
| PRIVATE_SOURCE_ALREADY_ON_GITHUB, но sandbox не умеет `git clone` | координатор/инфраструктура | продолжает source/API-backed работу; full build `NOT_RUN`, передаёт точный blocker координатору через журнал | **не требуется** до проверки альтернатив |
| Разрешённое локальное source/test изменение A/B | владелец соответствующего stream | исправляет, валидирует, публикует private branch | не требуется |
| Общий host/bridge/storage contract, например `kb-add` idempotency/receipt | координатор как интеграционный владелец | B оставляет `uncertain300`, готовит спецификацию/negative tests, не патчит shared без назначения | не требуется |
| Разрешение оплаты, публикация приватных данных, недопустимый риск или единственный физический UI gate | 👤 пользователь после проверки возможностей координатором | доказать gate, стоимость и альтернативы, подготовить единственный простой шаг | одно короткое решение/тест только если необходимо |

**Разрешение A:** `PodkinDmitry/xod-private:pilot/xod3-foundation` — существующий целевой source; `GitHub.fetch_file` может читать содержимое, но это не raw checkout в локальной runtime. В §98 подтверждено, что `git ls-remote` в sandbox не проходит DNS и нет PAT; ранние Node native 5/5 PASS по 40 строкам viewport не подменяют полную сборку/реальный redraw. **Нельзя выдавать требование пользователю скачать ZIP как единственный или первоочередной путь.** Изучить доступный runner, cloud build/CI (только после проверки cost safety) или доступный архиваж; при невозможности `FULL_BUILD=BLOCKED_ENV` и продолжить независимые source-backed изменения A. Оригинальную private Test13 ZIP не просить.

**Разрешение B:** в §104 непосредственно проверено, что существующий `extHandle('kb-add')` возвращает лишь `{ok,t}`, а generic `kbAddUrl214` не имеет idempotent duplicate protection по URL; `kbAddVideo214` по `yt` нельзя экстраполировать на статьи. B's `uncertain300` + nonempty host title receipt остается правильным fail-closed временным решением. Интеграционный владелец coordinator оценивает минимальный контракт `operationId` / атомарный dedup + устойчивый receipt или read-only query с `sourceId` и нормализованным URL (последний сам по себе не гарантирует exactly-once), возможные несовместимости и negative/regression tests. Общие `v224/m_kb214.js`, `m_yt220.js`, `m_mark224.js`, `ext224/bridge.js` не менять B без отдельного делегирования и доказательства совместимости. B может продолжить иную безопасную независимую работу и подготовить testcase, но не считать gate завершённым.

### 0.7.2. Обязательное завершение каждого хода

Каждый A/B executor после максимального безопасного цикла должен:

1. Сверить канонический `AGENTS.md`, рабочий журнал, private branch SHA и отсутствие чужой lease/изменений. Commit не равен acceptance.
2. Показать иерархический `release→lane→milestone→task→fixed criteria` и **доказательный** bar/Δ из §4.16, не украшение; `Δ=0` подписать.
3. Если есть непреодолимый blocker, записать *только в уже существующий журнал* `id / observed evidence / alternatives tried / why still blocked / owner=COORDINATOR / next independent task` под короткой CAS lease; **не** принуждать пользователя самому открывать и оценивать проблемы.
4. При наличии собственной следующей полезной независимой работы продолжать её автоматически **в рамках этого же вызова**; на границе хода выставлять **работающую** кнопку `Продолжить текущую задачу` или `Продолжить с обходом блокера` через `GenUI.issueNewTurn` и `button.onClick`, запускающую *новый ход только после клика пользователя*. Если таких UI actions клиент не предоставляет, один короткий trigger с копированием — не «напиши, что делать дальше» и не инертный элемент.
5. Не требовать ручной пересылки результатов из чата в чат, если их можно прочитать в canonical journal/private branch. При завершённой задаче кнопка следующего допустимого user-trigger ведёт к следующему accepted milestone; если critical approval нужен, кнопку нельзя превращать в обход approval.
6. Координатор при своём следующем trigger обязан читать новые `BLOCKED` и сам искать первую инженерно выгодную альтернативу прежде, чем просить пользователя о новых действиях.

**Сигнал пробуксовки:** новый список задач, коммитов, тестов или уточнений ≠ прогресс к интегрированной поставке; если 2 user-trigger подряд `Δ=0`, исполнителю запрещено бесконечно создавать дополнительные TODO без независимого пересмотра bottleneck. Прозрачная `Δ=0` допустима, если текущий шаг разумно подтверждает blockers, но тогда нужна новая гипотеза и по возможности owner handoff.

## 0.8. АТР P0: проверка живости критического пути, красный стоп и право завершить цикл без имитации работы (23.11.2026)

**Новое прямое решение 👤 пользователя**, приоритетнее прежних абстрактных «Продолжить всё». Один и тот же `TASK-COORD-AB-001` много циклов держится на `3/5=60%, Δ0`; отдельная GitHub Actions ветка обсуждения **остановлена пользователем, в ней не происходит работа**. Поэтому утверждение «ожидаем INFRA» без подтверждённой активной работы — не корректная модель состояния.

### 0.8.1. Прежде чем выбрать новую задачу — реальность владельца и зависимостей

В каждом ATR trigger executor/координатор сначала отдельно от обычного source HEAD проверяет **P0 critical-path live status**: (a) какой acceptance gate действительно не закрыт, (b) кто конкретный owner технического исполнения, (c) есть ли факт его активности/результата или только ярлык на чат, (d) возможно ли безопасно продолжить автономно здесь, (e) какой самый дешёвый подтверждённый маршрут к следующему gate, включая однократное действие пользователя. Записать в существующий журнал, только при существенном изменении:

`blocker_id | gate_id | technical_owner | activation_owner | activation_status | last_evidence | user_action_required | next_unblock_action`.

Строгие `activation_status`: `ACTIVE_VERIFIED` (проверенный запущенный процесс с evidence), `PAUSED_USER_REPORTED` (прямое сообщение пользователя), `NOT_STARTED`, `UNKNOWN`, `DONE_VERIFIED`. **Существование чата, назначения, PR и ветки НЕ означает ACTIVE**, обычный ChatGPT вообще не работает между пользовательскими вызовами. После остановки внешнего чата не «ждать» его будущий результат без нового запуска; нельзя самовольно сообщать, что он возобновлён. Различать `source_patch_ready` и `native_build/real_browser_active`.

### 0.8.2. Состояния и стоп-решение

- **🔴 `STOP`** — обязательная красная метка на верхнем уровне, если: (1) критический gate заблокирован внешним остановленным/незарегистрированным/неподтверждённо работающим владельцем и нет проверенного альтернативного runner, (2) требуемое пользовательское решение/запуск не сделаны, (3) минимум два последовательных user-trigger без accepted Δ + только подготовительные/второстепенные выходы, (4) обнаружен риск потери данных или интеграции, не допускающий безопасного продолжения. При этом соседняя подзадача может быть ACTIVE, но это **не отменяет** red для релиза.
- **🟠 `ATTENTION`** — один Δ0 на реально выполняемом критическом пути, активный владелец и конкретный ожидаемый проверяемый gate, без нужды в пользователе; не маскировать «активностью» выполнение без независимых фактов.
- **🟢 `MOVING`** — доказанная прибавка acceptance или выполняемая критическая задача с реальным runner/доказательством запуска (цвет ≠ процент); исходник прочитан, PR создан, журнал обновлён — не доказательство успеха.
- **`UNKNOWN` — не зелёный.** При приоритетной зависимости `UNKNOWN` означает предупреждение/красный stop до установления фактов, если это единственный следующий путь.

**Под красным STOP агент меняет поведение:** не запускает новую мелкую исходниковую работу, не пишет ещё один статус-журнал и не выводит кнопку «Продолжить», если прогнозируемый результат снова Δ0; сначала пытается короткий доступный non-premium маршрут и переоценивает stop. Если реально доступных инструментов/прав не хватает и user отсутствует — завершает ход как `STOPPED_WAITING_FOR_ACTIVATION`, даёт ровно одно человеческое действие или явно сообщает, что сейчас активной работы на critical path нет. Не выдавать негативную диагностику за «исполнение продолжено».

### 0.8.3. Контроль внимания и реактивация

Первое, что видит пользователь в ответе: `🔴 XOD 3.0 — СТОП`; за ним за **3–5 строк**: причина, то, что остановлено, что должен сделать конкретный владелец, progress/Δ. Подробности и SHA — в existing GitHub journal. Активная пятирівневая ветка из §0.6 остаётся видимой компактно (root/stream/milestone/task/criteria), но не вытесняет главную проблему. Красный — только реальный P0/риск; в обычных прогрессах не устраивать многоцветный дашборд. Никаких неработающих кнопок.

**Реактивация не обязана быть именно GitHub Actions.** Требуется единственный реально доступный runnable private-source test path с доказанной безопасностью и без дополнительных расходов без согласия: согласованный GitHub Actions, уже разрешённый другой cloud runner или точечный manual gate только после проверки низкой стоимости. Если остановлен сам infra-чат, пользователь может один раз перезапустить именно его и отправить заранее подготовленный prompt; кнопка в координаторском чате не может запустить другой чат. Другая альтернатива допускается только после конкретной проверки доступности и стоимости, без повторения прежних бесконечных исследования/переноса/ZIP.

**Факт на 23.11.2026:** `XOD-REL-C4-C5-RUNNER`, `critical_path=RED_STOP`, `infrastructure_chat=PAUSED_USER_REPORTED`, `build C4=NOT_RUN`, `browser C5=NOT_RUN`, `A+B readiness 3/5=60%, Δ0`. Источники: journal §§120–126, private draft PR #1; прямое сообщение 👤 пользователя о прекращённой инфраструктурной работе. `A/B` могут проводить отдельные source-backed исправления, но нельзя показывать от этого зелёный для XOD 3.0. Смена на `MOVING` — только после доказанного запуска/успеха критического пути; изменение `PAUSED_USER_REPORTED` требует факта нового запуска, не догадки.
