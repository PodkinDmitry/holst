# XOD · протокол продолжения: GPT-6 High вручную, Scheduled в резерве

**Версия 1.2 · 2026-11-21.** CHAT GPT-6 High выполняет независимую разработку **только при SOL_STATE=SLEEPING**. При доступности Work управление возвращается 🟩 SOL как **главному оркестратору XOD**, а не исполнителю отдельного интеграционного задания. Пять Scheduled-задач приостановлены, доступный Scheduled ограничен Medium.

## Контракты
- Канонический журнал: `ai-workspace/handoffs/work-resume-latest.md`; всегда читать текущие `SOL_STATE` и `WORK_EXECUTION`, а не полагаться на прежнее `SLEEPING`.
- Канонический формат сообщений: `ai-workspace/protocols/xod-response-format.md`.
- Блокировка: `ai-workspace/handoffs/chat-run-lock.json`.
- Рабочий код/тесты: `ai-workspace/submissions/chat-NN` в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Не менять `main`.
- 🟩 SOL — **главный стратегический руководитель и оркестратор XOD**. 🟦 CHAT самостоятельно работает только пока SOL спит; после пробуждения — по реальному делегированию SOL. 👤 ДИМА — только важные решения и переход в Work.

## 1. Общие гарантии каждого цикла
1. Прочти актуальный журнал. Если SOL_STATE != SLEEPING — не разрабатывай, **поставь на паузу свою запланированную задачу**, если доступен Automations update, и явно сообщи об ограничениях, иначе остановись.
2. Прочти lock и его blob SHA. Если `state=running` и срок `expires_at` в будущем — не начинать параллельную работу. Если idle/истекло — захвати через GitHub update_file с текущим `sha` (оптимистическая блокировка). При конфликте SHA остановись. Выбирай уникальный owner на каждый запуск.
3. Lock lease до 70 минут, но после завершения обязательно освободи. Если работа длится дольше 15 минут — обновляй heartbeat и продлевай expires_at по актуальному sha. Перепроверяй блокировку и SOL_STATE перед каждым существенным коммитом. Не изменяй чужие данные и не форсируй SHA.
4. Работай максимально содержательно: тесты, воспроизводимые дефекты, высокоценный автономный патч, модуль, непрерывные проверки, но избегай фантазий об актуальной локальной сборке SOL. Используй оригиналы в GitHub; сохраняй неинтегрированные исправления SOL. У задачи должен быть наблюдаемый результат, а не «видимость деятельности».
5. После каждого существенного результата **обновляй существующий журнал** с выполненным, проверенным, непроверенным, ссылками, рисками и следующим действием. Оставь checkpoint, чтобы следующий запуск не повторял работу. Если остаётся полезная самостоятельная работа — продолжай в текущей итерации, а не останавливайся ради расписания.
6. Заверши с коротким отчётом по каноническому формату, освободив lock, если owner совпадает. Ошибки/недоступность инструментов не скрывать; результаты тестов заявлять только при фактическом исполнении.

## 2. GPT-6 High · основной режим с минимальным участием

**Сфера:** только существующий **чат разработки XOD** в состоянии `SOL_STATE=SLEEPING`, где 👤 ДИМА выбрал GPT-6 High. **Не выполнять разработку XOD в ветке разговора про настройку автоматизаций**. Выбранную модель инструментами GitHub, DIL, автозадачами или промптом программно установить/проверить нельзя; параметр High должен быть выбран в меню ChatGPT.

### 2.1. Одноразовая инициализация в чате XOD

👤 ДИМА отправляет в рабочий XOD-чат подготовленную команду **только при SOL_STATE=SLEEPING**. Затем 🟦 CHAT в итоговых ответах до пробуждения SOL, когда доступна автономная работа, добавляет работающую кнопку **«Продолжить XOD · GPT-6 High»**, вызывающую host action `GenUI.issueNewTurn` **из прямого клика пользователя**, с краткой командой «продолжи по каноническому протоколу и GitHub checkpoint». Кнопка в чате настройки автоматизаций не должна незаметно запускать код XOD.

### 2.2. Загрузка и выполнение одного запуска

1. Прочитать канонический GitHub-журнал и его **текущий** `SOL_STATE`. Не делать вывод о пробуждении SOL по времени. Если состояние не `SLEEPING`, **не продолжать автономную разработку**.
2. Проверить действующий lock, захватить его через обновление с текущим SHA. Если lock занят — не ждать, не форсировать и не работать параллельно. В момент каждого существенного GitHub-коммита перепроверять lock и SOL_STATE.
3. Выбрать следующий **реально полезный** блок по состоянию исходников/реестру незавершённого, не создавать новую параллельную дорожную карту и не дублировать выполненную работу. Один вызов GPT-6 High должен охватывать **несколько логически связанных этапов**, где это безопасно: воспроизведение → исправление → тесты → commit → checkpoint → следующий автономный шаг. Не останавливаться после первого мелкого результата, если доступны следующие независимые шаги.
4. После каждого существенного блока обновлять журнал, фиксировать конкретные проверки, URL файлов и незавершённые риски. Перед завершением безопасно освободить lock, если он ещё принадлежит текущему сеансу.
5. В отчёте использовать канонические рамку и цитаты, **одну кнопку продолжения**. Не просить подтверждений на обратимые решения. Не утверждать, что модель работала в фоне или что пользователь не нужен, если возник настоящий блокер.

**Важно:** один клик запускает **один следующий ход в этом чате**, а не бессрочный фон. Автоматического повторного запуска GPT-6 High через Plus в подтверждённом доступном интерфейсе **нет**. Время хода нельзя гарантированно удлинить одним текстом промпта. Соотношение полезной работы и количества кликов оптимизируется размером задач, самопроверками и контрольными точками.

## 3. Исторический Scheduled Medium и ограничения
- Все запуски читают общее состояние из GitHub, а не предполагают общий контекст между отдельными чатами.
- Не включать Work/Codex и платный API. Scheduled CHAT может потреблять usage allowance Plus.
- **Выбор модели в Scheduled UI:** 👤 ДИМА экспериментально подтвердил Medium без опции High; то же произошло при создании одноразовой задачи из обычного High-чата. **Не утверждать поддержку High в Scheduled.** На Plus Extra High/Pro не входят в обычный доступ. Программно через доступный Automations API модель не меняется.
- Пять почасовых Scheduled-задач сейчас **paused**. При их явном будущем включении они не гарантируют запуска точно по минутам; возможны задержки, блокировки, лимиты и остановки.
- После сигнала 👤 ДИМЫ о доступности Work приостановить независимую CHAT-разработку и Scheduled, подготовить передачу **управления** по §4. Не считать запуск Work выполненным без реального подтверждения. Новые ID задач фиксировать в журнале.


## 4. Обязательное восстановление руководства 🟩 SOL после доступности Work

**Ошибка, которую нельзя повторять:** при возвращении Work накопленные CHAT-пакеты не становятся новой стратегией и не должны превращать SOL в исполнителя отдельного integration ticket. Историческое узкое поручение из журнала §23.1 **заменено §24**. Последующие прямые решения 👤 ДИМЫ имеют приоритет над любыми сохранёнными протоколами.

### 4.1. Переход состояний
- **SOL_STATE=SLEEPING:** CHAT вправе самостоятельно работать в разрешённых границах с GitHub lease.
- **SOL_STATE=AWAKE, WORK_EXECUTION=NOT_STARTED:** 👤 ДИМА сообщил, что Work снова доступен, но SOL **ещё не доказал реальный запуск**. CHAT прекращает новую независимую разработку и готовит единую передачу управления для существующего Work-чата. Не изображать SOL уже запущенным.
- **WORK_EXECUTION=STARTED/RUNNING:** только после фактического подтверждения запуска или результатов Work. CHAT получает новые задачи по подтверждённому делегированию SOL; не заявлять, что другой чат автоматически увидел GitHub или получил поручение.

### 4.2. Первые действия SOL
1. Прочитать актуальный журнал целиком, §24 и более поздние решения; исходную стратегию XOD 3.x, историю собственных изменений, реальную доступную сборку и **все** результаты CHAT, созданные во время сна. Невозможность прочитать материалы обозначать открыто.
2. Восстановить точку A: что действительно интегрировано, что было лишь проверено на независимом стенде, какие патчи альтернативны, на что опираются и какие могут потерять данные. Защитить локальные изменения SOL и реальные пользовательские данные.
3. Проверить стратегическую очередность **XOD 3.0 «Фундамент» → 3.0b «Критичные ошибки» → более поздняя 3.3 (YouTube)**, если она не изменена более поздним решением 👤 ДИМЫ. Множество CHAT-пакетов YouTube не повышает автоматически их стратегический приоритет.
4. **SOL сам руководит** приоритетами, исполнителями, распределением задач, расходом Work, интеграцией, регрессиями, критическим путём и документами; сам выбирает и выполняет следующий высокоценный безопасный блок. Не ограничивать возвращение отчётом или одной интеграцией. Делегировать только действительно доступным агентам, не предполагать прямую коммуникацию между чатами.
5. Поддерживать тот же канонический журнал и план, решение о принятии каждого пакета, доказательства проверок, назначения и ограничения. Не менять main без разрешения и не утверждать интеграцию по fake-CAS.

### 4.3. Передача в другой чат: GitHub-first, буфер только при необходимости

Если целевой агент имеет доступ к GitHub, при своём новом ходе он **самостоятельно читает** актуальные AGENTS.md, журнал, протоколы, стратегию и поручения. Не заставлять пользователя переносить длинный бриф или данные между чатами; GitHub является общей рабочей памятью. Это правило согласовано с xod-response-format.md §4.10 и заменяет более раннее требование всегда готовить полный буферный handoff.

Отдельный Work-чат не начинает работать только из-за публикации GitHub: пользователь должен его вызвать (если нет внешнего запуска). При необходимости дать **короткую команду запуска**: «SOL, прочитай последние AGENTS.md и ai-workspace/handoffs/work-resume-latest.md в PodkinDmitry/holst (ai-workspace), восстанови руководство всем XOD, проверь источники, текущую сборку и блокировку, самостоятельно продолжай по самому свежему состоянию». Кнопка копирования короткой команды — только если полезна; полный самодостаточный бриф — резерв на случай недоступности GitHub адресату. GenUI.issueNewTurn не отправляет сообщение в другой чат, а GenUI.copy не отправляет сообщение вообще.

**Правильный первый императив:** «🟩 SOL, верни управление всем XOD: восстанови стратегию и фактическую сборку, проверь весь период сна и все CHAT-пакеты, сам назначай работы и выполняй следующую максимальную по пользе задачу». Конкретные интеграционные задачи SOL выбирает как подзадачи после аудита.
