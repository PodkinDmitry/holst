# XOD · протокол исполнения: один ответственный исполнитель; Work в резерве

**Версия 1.8 · 2026-11-22 · прямое утверждение пользователя.** Новая модель заменяет обязательное разбиение на отдельные планирующий и исполнительный чаты; её цель — проверенный продуктовый результат с минимумом ручных действий и премиальных расходов. Раньше обязательная последовательность CHAT-PLAN → CHAT-EXEC → SOL вынуждала пользователя многократно вручную запускать и связывать сессии. Это отклонение от целевой автономности. Наличие ролей, журналов и чекпоинтов не является продуктовым результатом.

## 0. Действующий цикл: один владелец результата (приоритет над разделами 1–4)

1. **Назначение.** Прямое поручение пользователя делает текущего доступного агента владельцем результата в пределах его реальных инструментов. По умолчанию он сам анализирует, выполняет, проверяет, исправляет, документирует и выдаёт либо **готовую проверенную версию**, либо воспроизводимый blocker. Не предлагать отдельный CHAT-EXEC или SOL, пока действующий агент может закончить доступную часть сам. Стратегический авторитет SOL исторически сохраняется, но Sol как модель **недоступен** при заявленной исчерпанной недельной квоте; нет ожидания или фиктивной межчатовой передачи.
2. **Единая рабочая итерация.** Определи минимальный вертикальный срез с измеримой ценностью и критериями, проверь актуальный GitHub/код/зависимости, захвати законную CAS lease, исполни максимум в текущем ходе, запусти детерминированные QA, сам исправь замеченные ошибки, запиши только существенную дельту и readback, освободи lease. Статусы `PUBLISHED`, `STARTED`, `VERIFIED`, `INTEGRATED`, `ACCEPTED` доказывай отдельно; исходниковый PASS не превращай в release PASS. Если пользовательское утверждение реально необходимо — короткий выбор один раз; в остальных случаях действуй.
3. **Длительность CHAT — не подтверждена фиксированным пределом.** Пользователь наблюдал ≈6 минут, позднее ≈8 минут; это гипотеза о возможных timeouts, а не измеренный универсальный cap. Никакого принудительного 5+1 minute limit или 4–7 запусков как плана до релиза. Работай максимально полно до фактической остановки/ограничения, контролируй real elapsed time и сохраняй проверяемый checkpoint; отдельно считай человеческие действия, model/tool runtime, autonomously running scripts и календарное ожидание. Инженерные часы/6 минут не являются числом сессий. Для длинного теста использовать независимый script/CI, а не ожидание премиальной модели.
4. **Управление стоимостью.** По последнему пользовательскому сообщению недельный премиальный остаток равен 0%, не измерен из ChatGPT UI. Без premium Work, Sol, Astra, платного API/перерасхода. При неизвестном остатке — сначала доступное подтверждение. >10%: только точечно с верхней границей; 5–10%: премиум-старт лишь после нового прямого разрешения; <=5%: остановить некритичное; 0%: не запускать. Любая платная операция требует `scope / why cheap unavailable / budget ceiling / stop loss / release reserve / model / snapshots before-after`. Протокол не может физически ограничить лимиты платформы: честно показывать эту границу. Статистика без snapshots — UNKNOWN.
5. **Передача между агентами — только при положительном выигрыше.** Сначала исследуй собственные инструменты: при наличии локального checkout, GitHub и CLI делай работу сам. Отдельный агент оправдан только отсутствующим критическим доступом, доказанным рисковым конфликтом или независимым специализированным тестом, ценность которого превышает цену передачи. Пользователь не обязан пересылать промежуточные документы/JSON, пока у текущего агента есть иной путь. Новые отдельные чаты пользователь запускает только когда это действительно необходимо; никакой иллюзии отправки соседнему агенту.
6. **Управление незавершёнными решениями без напоминаний.** В конце содержательных ответов по текущему проекту и при смене темы коротко показывай важные `PENDING_APPROVAL / APPROVED_NOT_PUBLISHED / PUBLISHED_NOT_EXECUTED / BLOCKED` с владельцем и следующей проверкой. Не прячь ожидание решения в длинном документе, прямо предупреди, если уходишь к другому вопросу. Уже принятое решение не спрашивай снова. Не создавать календарные/периодические напоминания из этого принципа.
7. **Выполнение и безопасность.** Перед записью всегда свежие `AGENTS.md`, журнал, lease и relevant protocols. Живую чужую lease не перехватывать. Просроченную lease — только CAS и при наличии самостоятельного разрешения/доказательства отсутствия работы; документируй reclaim. Не меняй `main` без разрешения, не публикуй приватные данные или точный полный source. Нельзя объявить завершённой локальную интеграцию, если у агента нет доступа к ней. Пользователь явно сообщил, что SOL больше недоступен, а окончание доступности не означает завершение 3.0.
8. **Сценарный бюджет, НЕ замер:** остаток 3.0 = 9–23 активных инженерных часов плюс 5–10 ч резерва; вся оставшаяся цепь 3.0–3.6 = 218–459 ч плюс резерв 5–10 = 223–469 ч. Доказанных данных для числа CHAT-сессий до релиза НЕТ; прежний 4–7-цикл признан необоснованным предсказанием. Новая локальная автоматизация сборки **не является** эмпирическим сокращением часов написания кода и не оправдывает произвольное уменьшение этих диапазонов. Показатели выдавать раздельно: latency ответа, execution minutes, часы инженерной работы, wall time автономных тестов, user actions, Work %. Полная карта 8 этапов / 37 подшагов и её 5 метрик сохранены в response-format §§4.6–4.8, 4.13.

**Переход управления по сообщению пользователя 22.11.2026:** SOL quota exhausted, текущая деятельность SOL прервана, доступный CHAT теперь выполняет утверждённую реорганизацию стандартов; код и фактическая release acceptance остаются такими, как указано в последнем проверенном journal §71. Планирующая/исполнительная специализации — необязательные роли внутри единого исполнения, а не требование ещё одного чата.

### 0.1. Эмпирический аудит оригинального Claude Export (22.11.2026): что ускоряет **результат**, а не ответ

По прямому запросу пользователя прочитан оригинальный приватный архив `Claude Export  17 11.zip` из личной Library, включая оригинальные `conversations-000.zip/conversations.json` и блоки `tool_use`; в GitHub **не публиковать** тексты диалогов, приватные команды/секреты, вложения и исходники. В экспорте **93 диалога, 1 255 сообщений и 9 323 вызова инструментов**. Два основных диалога разработки `HOLST` и `HOLST 2` содержат 147 + 40 сообщений и соответственно 4 775 + 1 026 = **5 801** вызов инструмента (в т.ч. 4 147 Bash). Источник — наблюдаемые блоки и timestamp; количество вызовов НЕ равно числу успешных правок.

**Проверяемые полные пользовательские рабочие циклы в `HOLST 2` (время между запросом и последним ответом до нового запроса, не токены и не чистое CPU-время):**

- Холст 2.23: ~114.3 минут, **403** вызова; проверка build/test/исправление регрессий и архивы для пользователя.

- Расширения 2.25/2.26: ~16.5/29.7 мин, **17/25 Bash-команд**, версии выданы; настоящая YouTube-проверка явно **не выполнялась**.

**Вывод, не измеренный коэффициент ускорения:** прежняя кажущаяся «10×» эффективность связана прежде всего с **одним пользовательским поручением → десятки/сотни команд в длительно живущей среде → сразу готовые ZIP/артефакт + тесты + список только необходимых действий пользователя + один devkit/START.md для следующей итерации**. Это не «другой моделью за 6 минут сделана двухчасовая работа». Не подменять эту архитектуру 4–7 вручную запускаемыми шестиминутными CHAT-сессиями и не обещать `4–7` до релиза; этот старый ориентир сохраняется только как неподтверждённый ближайший организационный цикл, не как цель эффективности.

**Практический действующий контракт:** для полноценного Claude-подобного цикла нужен *фактически доступный* долгоживущий исполняющий контур с исходным checkout, правом исполнения скриптов, хранением файлов/кода и возможностью довести до проверенного артефакта. При его отсутствии стандартный чат может выполнять только реально доступный вертикальный срез; не обещать фоновое исполнение и не перекладывать на пользователя 100+ запусков. Стараться при доступной среде паковать тесты, сборку, исправления и релиз в **одну завершаемую задачу**, а не в десятки межчатовых сообщений. **Качество:** отдельно отмечать тестируемые локальные/синтетические проверки и непроверенные browser/cloud gates; скоростные архивные релизы не заменяют приёмку.

### 0.2. Реально проверенный офлайн-цикл сборки и тестов: `xod-cycle.py` (22.11.2026)

**Новый канонический исполняемый инструмент, без сторонних платных сервисов:** [ai-workspace/tools/xod-cycle.py](../tools/xod-cycle.py). Python 3.10+, а для синтаксической проверки JS нужен установленный Node.js; `--browser-test` требует действительно установленный Playwright Chromium. Запускается только по прямой команде агента/пользователя в реальной среде; **GitHub-публикация Python-файла не создаёт запущенного фонового агента на Windows пользователя.** Не включать autorestart/watchdog, не устанавливать программы пользователю без необходимости. Скрипт читает ZIP/каталог из доверенного источника, создаёт временную изолированную копию, выполняет выбранную recipe, собирает пакет, пишет `cycle.json` + `cycle.log` + SHA256. Не меняет входной ZIP, `main`, реальный Test13, облако, приватную доску и не отправляет данные в сеть; **исходные скрипты проекта могут иметь свои сетевые действия**, поэтому доверие к исходнику — предусловие.

**Режимы:** `legacy224` (`v224/patch224.py` → `holst.html` → проверки `node --check` → ZIP приложения и расширения) и `xod3` (`build.py dist` → пакет `dist/`, при явном `--browser-test` — `tests/app_regression.py`). Не подразумевать одинаковую структуру всех Test13; если recipe не подходит, gate BLOCKED и нужна адаптация по **действительному source**, не ложный успех. Автоматическое определение предпочитает `xod3`, когда есть `build.py`.

**Доказательство из текущего runtime, а не будущий эффект:** по настоящему `holst-devkit-2.24.zip` исходного пользователя изолированный `legacy224` build + inline Node.js syntax **PASS**, app ZIP + extension ZIP + standalone HTML получены, ZIP-slip negative test **BLOCKED как положено**, рабочий отчёт показывает `product_release_accepted=false`, Drive `NOT_RUN`. Обычный цикл после локальных файлов ~2.0–2.5 сек в данной среде; не объявлять это временем разработки 3.0. При `--browser-test` smoke корректно вернул `BLOCKED_ENVIRONMENT` из-за отсутствующего Playwright Chromium executable; пакет **сохранён**, но browser PASS не заявлен. Это проверка сборочной автоматизации **старой 2.24**, не XOD 3.0, не Chrome/Edge на компьютере пользователя. Истинная live Test13/Drive/производительность всё ещё требуют текущего host checkout.

**Действующий контракт для внедрения в проект:** сначала пытаться использовать один scriptable цикл, а не требовать от пользователя повторно запускать 4–7 чатов; мерить исход/время/цену по реально выполненным итерациям, не по токенным фантазиям. При отсутствии доступа к реальному Test13 не форсировать подмену source файлом 2.24; это ограничение доступа, а не повод для премиального SOL. Пример только для доверенного архивного devkit:
```bash
python ai-workspace/tools/xod-cycle.py --source holst-devkit-2.24.zip --out ./xod-cycle-out
```
Чтобы проверить браузер **после установки поддерживаемого browser executable**, добавить `--browser-test`; при отсутствии браузера не получать PASS. `--out` должен быть новым/пустым, чтобы не потерять старые результаты.

### 0.4. Публикация патча с проверкой точных байтов (22.11.2026)

Фактическая ошибка CHAT43–45: передача `.patch` через временную Library + Files read иногда **отбрасывала заключительный перевод строки**. После этого `git apply` отвечал `corrupt patch`, хотя локально исходный патч применялся. Это не дефект продукта, но блокирует применение уже проверенного исправления. Все три опубликованных патча исправлены до исходных байтов 22.11.2026.

**Обязательный минимальный приёмочный gate для source-only патчей:** после записи в GitHub прочитать файл заново и сверить `blob SHA` с Git blob SHA исходного локально проверенного файла (включая терминальный `\\n`), а также `git apply --check` для точно этих байтов на изолированной копии подтверждённого исходного модуля. `content readback` после промежуточной текстовой передачи без побайтовой SHA-проверки недостаточен. При выявлении разницы восстановить исходные байты через SHA/CAS `update_file`, не считать устаревший commit принятым. Не загружать приватный source в GitHub, публиковать только узкие патчи и тесты.

## Исторический протокол CHAT-PLAN → CHAT-EXEC (необязателен; при противоречии действует §0)

## Контракты
- Канонический журнал: `ai-workspace/handoffs/work-resume-latest.md`; всегда читать текущие `SOL_STATE` и `WORK_EXECUTION`, а не полагаться на прежнее `SLEEPING`.
- Канонический формат сообщений: `ai-workspace/protocols/xod-response-format.md`.
- Блокировка: `ai-workspace/handoffs/chat-run-lock.json`.
- Рабочий код/тесты: `ai-workspace/submissions/chat-NN` в ветке `ai-workspace` репозитория `PodkinDmitry/holst`. Не менять `main`.
- 🟩 SOL — **главный стратегический владелец XOD и интеграционный авторитет**; 🟦 CHAT-PLAN — пользовательский операционный планировщик; 🟦 CHAT-EXEC — отдельно запускаемый пользовательским сообщением исполнитель, при актуальном журнале `WORK_EXECUTION=COMPLETED / NEXT_AGENT=CHAT` и свободной lease. Прямое поручение 👤 ДИМЫ подтверждает ограниченную автономию CHAT-EXEC, не является стартом Work или интеграцией SOL. Предыдущие Scheduled задания не возобновляются автоматически.

## 1. Общие гарантии каждого цикла
1. Прочти актуальный журнал. **Scheduled/автономные фоновые задачи** не начинают разработку, когда SOL_STATE != SLEEPING. **Исключение только для свежего прямого поручения пользователя отдельному CHAT-EXEC** при `SOL_STATE=AWAKE + WORK_EXECUTION=COMPLETED + NEXT_AGENT=CHAT` и документированном task assignment; если `NOT_STARTED`, `STARTED`, `RUNNING` либо назначение отсутствует, исполнитель останавливается. Любую живую lease другого агента не обходить.
2. Прочти lock и его blob SHA. Если `state=running` и срок `expires_at` в будущем — не начинать параллельную работу. Если idle/истекло — захвати через GitHub update_file с текущим `sha` (оптимистическая блокировка). При конфликте SHA остановись. Выбирай уникальный owner на каждый запуск.
3. Lock lease до 70 минут, но после завершения обязательно освободи. Если работа длится дольше 15 минут — обновляй heartbeat и продлевай expires_at по актуальному sha. Перепроверяй блокировку и SOL_STATE перед каждым существенным коммитом. Не изменяй чужие данные и не форсируй SHA.
4. Работай максимально содержательно: тесты, воспроизводимые дефекты, высокоценный автономный патч, модуль, непрерывные проверки, но избегай фантазий об актуальной локальной сборке SOL. Используй оригиналы в GitHub; сохраняй неинтегрированные исправления SOL. У задачи должен быть наблюдаемый результат, а не «видимость деятельности».
5. После каждого существенного результата **обновляй существующий журнал** с выполненным, проверенным, непроверенным, ссылками, рисками и следующим действием. Оставь checkpoint, чтобы следующий запуск не повторял работу. Если остаётся полезная самостоятельная работа — продолжай в текущей итерации, а не останавливайся ради расписания.

## 4. Обязательное восстановление руководства 🟩 SOL после доступности Work

**Ошибка, которую нельзя повторять:** при возвращении Work накопленные CHAT-пакеты не становятся новой стратегией и не должны превращать SOL в исполнителя отдельного integration ticket. ### 4.1. Переход состояний
- **SOL_STATE=SLEEPING:** CHAT вправе самостоятельно работать в разрешённых границах с GitHub lease.

- **WORK_EXECUTION=STARTED/RUNNING:** только после фактического подтверждения запуска или результатов Work. CHAT получает новые задачи по подтверждённому делегированию SOL; не заявлять, что другой чат автоматически увидел GitHub или получил поручение.
