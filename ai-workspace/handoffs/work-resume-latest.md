Вместо этого увеличивать полезность одной итерации и продолжать несколько последовательных независимых задач, пока хватает времени исполнения.

При живом lease или конфликте SHA новый запуск не начинает работу. Каждые ~15–20 минут в долгой итерации lease продлевается. В конце сбрасывать на `idle` только при прежнем `owner`. При аварии lease истекает; очередной запуск пробует снова. Это best-effort защита при условии соблюдения протокола каждым запуском, а не гарантия против внешних неконтролируемых агентов.

### 11.1. Приоритет 1 — штатный поминутный запуск внутри чата

Официальная документация OpenAI [Scheduled tasks — ChatGPT Learn](https://learn.chatgpt.com/docs/automations), раздел «Schedule a task inside a chat», **прямо указывает**, что scheduled tasks **inside a chat can use minute-based intervals**. Это наиболее близкое к желаемому циклу 7 минут с сохранением контекста. **Но** доступный CHAT интерфейс Automations tool в этом сеансе допускает *не более одного запуска в час*; наличие настроек 7 минут в UI конкретного аккаунта **не подтверждено**. На Plus максимум 5 одновременно активных scheduled tasks, см. [Help Center](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt). Важно: запланированный запуск в Chat может расходовать allowance/credits плана, даже не публикуя отчёт. **Эксперимент:** в Scheduled открыть/создать задачу *внутри этого чата*, проверить настройку «каждые 7 минут». Если доступна — использовать общие GitHub checkpoint/lease; если нет — не обещать обхода.

### 11.2. Приоритет 2 — Windows Task Scheduler + исполнитель

Планировщик задач Windows умеет частые повторные запуски (Microsoft Learn: https://learn.microsoft.com/en-us/windows/win32/taskschd/repeating-a-task). Рекомендуемый внешний исполнитель: бесплатная **локальная** модель через Ollama (при достаточном ПК) либо доступный бесплатный тариф Gemini Developer API (регион/модель/лимиты проверяются при настройке; по бесплатным запросам возможно использование данных для улучшения продуктов). Повтор каждые 7 минут, **если задача активна — не запускать дубликат**, общий GitHub lease/heartbeat, сохранение diff+тестов в ai-workspace. Требуются однократная настройка ПК/ключа и включённый ПК. **Это не запускает обычный ChatGPT Plus chat**, а отдельную модель/скрипт. OpenAI API не включён в подписку Plus.

### 11.3. Приоритет 3 — GitHub Actions в облаке

GitHub Actions позволяет [cron минимум раз в 5 минут](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax); стандартные runners в публичном repo [бесплатны](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Для AI-исполнения нужен сторонний бесплатный API/локальный runner либо оплачиваемый API — самого GPT Chat запуска cron не даёт. **Важно**: workflows типа schedule выполняются из *default branch*, значит для текущего `holst` нужно добавить минимальный workflow YAML в `main` (или поменять default branch/создать отдельный repo), что противоречит текущему запрету менять main и требует явного решения 👤 ДИМЫ. Время старта может задерживаться, нет строгого SLA. GitHub Models inference API уже **выключен с 30.07.2026**: https://github.blog/changelog/2026-07-01-github-models-is-being-fully-retired-on-july-30-2026/ — **не предлагать его как бесплатный движок**.

### 11.4. Нулевой технический барьер — минимальный ручной сигнал

Пока полное решение не развёрнуто, по завершении каждого чат-блока показывать 👤 ДИМЕ **одну кнопку «Продолжить XOD»** в текущем чате. Она отправляет короткое сообщение, требующее сначала прочитать GitHub checkpoint, проверить SOL_STATE и lock, затем автономно продолжить. При 1 действии на завершённый блок не нужно скачивать, переносить или писать инструкции. Это не безлюдный запуск, но мало внимания. Не автоматизировать клики в интерфейсе ChatGPT через непроверенные расширения/скрипты.

### 11.5. Дополнительные методы, исключения и решение

- Несколько **различных** специализированных hourly tasks можно разнести по минутам, например анализ/тесты/документация. Но лимит 5 активных задач Plus, пересечения и повторная загрузка контекста снижают выгоду; не создавать дубликаты только для обхода частотного ограничения.
- Event-triggered задачи GitHub/OpenAI запускаются через **Work**, а не обычный бесплатный CHAT (Help Center); не соответствуют цели экономии Work.
- OpenAI Dots как always-on агент пока **не входят в Plus**: Pro/Business Premium/Enterprise and eligibility, https://help.openai.com/en/articles/20001530-getting-started-with-your-dot; отдельная платная архитектура не подходит.

**Вывод/следующий эксперимент:** сначала проверить доступность **7-минутной in-chat Scheduled** (официально описана, но в данном tool недоступна); при отрицательном результате — применять ручную кнопку без лишнего текста или развернуть локальный/облачный бесплатный исполнитель как отдельную систему. Во всех сценариях держать Sol asleep до сообщения 👤 ДИМЫ, архив/журнал в GitHub — единственный источник состояния. Опция не считается реализованной, пока не показан рабочий прогон.

### 15.2. Целевая гибридная система

`GitHub checkpoint → Antigravity CLI Free (автономный код/тесты, наивысший доступный effort) → git branch/patch/CI → обычный ChatGPT GPT-6 High (точечный сложный аудит/архитектура с одним нажатием 👤 ДИМЫ) → SOL (реальная интеграция после пробуждения)`.

- **Оптимизация непрерывности:** вместо серии таймеров, которые каждые 7 минут повторно заставляют модель перечитывать проект, давать `/goal` **одну крупную ограниченную цель** (например «закрыть три рискованных сценария, автономно реализовать, прогнать тесты, зафиксировать всё в GitHub»). Пока задача выполняется, нет искусственного обрыва через несколько минут. После завершения новая цель стартует через локальный оркестратор или вручную одним действием. Для устойчивой работы между сессиями использовать Windows Task Scheduler как watchdog / повторное выполнение `agy -p`; выполнять **не более одного экземпляра**, проверять GitHub lease и SOL_STATE, сохранять checkpoint.
- **Безопасность:** отдельная ветка `ai-workspace`, не `main`; sandbox + запрос подтверждения для опасных shell/git операций; никакого обхода квот; без платного оверейджа; не сохранять credentials в публичный GitHub; не давать агенту автоматически merge/push в main. ### 29.1. Нормативный маршрутизатор в пределах одного Work-чата

| Режим | Рекомендуемая модель Work, если доступна | Когда использовать | Проверка/ограничение |

| **Исполнитель** | **Terra · Low/Medium** | Предсказуемые типовые изменения по готовому patch+контракту, запуск регрессий, исправления узких lint/test FAIL, упаковка тестовых артефактов | Дать тесты и acceptance; при неверных результатах не повторять бесконечно, эскалировать |

**Приоритет затрат:** для простых операций выбрать самый экономичный способ (локальный скрипт без моделей, готовые CLI-тесты, затем Luna, Terra, Sol, Astra). ### 29.2. Пилотная проверка экономии и обратное переключение

1. В существующем Work-чате 🟩 SOL/любая модель с доступом выбирает **одну безопасную детерминированную задачу** (пример: прочитать пять заранее указанных файлов, перечислить commit SHA, запустить предоставленный test gate, сохранить краткий результат без касания main).

3. Проверить корректность результата: file SHA, коды завершения тестов, изменённые строки, отсутствие нежелательных записей. Сверить пятичасовой и недельный остатки перед/после. Модели внутри Work используют один пул; отличие только **скорость расхода**, не новая бесплатная квота.

5. По 2–3 сопоставимым, действительно завершённым пакетам рассчитать **суммарный расход квоты до/после, время, точность и стоимость исправлений**. Экономия = baseline Work Sol за тот же объём минус Luna/Terra + review/retry cost, без вымышленных коэффициентов. Целевые проценты **не установлены**, пока нет контрольного измерения. При ограниченном недельном остатке ≤10% начать с минимального безопасного пилота, не делать массивный эксперимент по цене как отдельную кампанию.

**Отдельный риск:** нельзя выдавать принятый план дешёвым оператором за фактический интеллектуальный надзор мощной модели в фоне.
